### §1.4 `--xla_gpu_deterministic_ops=true` 開著時壓縮版梯度會錯(問題紀錄第八節,⚠️ 決定擱置)

**2026-09-08 重新特徵化(細節見問題紀錄第八節「2026-09-08」段)**:

- **觸發條件**:外層 batch `jax.vmap`(batch ≥ 2)+ `jax.grad` + flag。`ConvNetCompressed.apply_batched` 符合。實測 `dL/dW` rel ≈ 0.4–0.5;batch=1 正常;跟 fire、`event_gain` 都無關。
- **不是一般 gather,也不是佇列建構**:同樣 batch-vmap 的密集參考實作 flag 開著仍正常;`sum(build_conv_queue_compressed(...).maps.b)` 單獨 batch-vmap 也正常 → bug 在 **`run_layer_forward` 的 backward(滑窗 clip-gather vmap + `lax.scan` reverse-mode)在外層 batch vmap + flag 下**。舊說法「還有兩處沒堵的 gather」「`safe_k_y`/`safe_k_x` clip 是修法」都被推翻——clip 無害但不是關鍵,batch=1 不 clip 也對、batch≥2 clip 了也錯。
- **forward 不受影響**:flag 開/關 v_final 逐位元相同。要跟 CSNN-FPGA 做 bit-exact 硬體驗證(比對 forward),flag 可以開。
- **flag-off 非決定性量級**:每步 ~1e-7 相對(float32 epsilon),400 步內階梯式放大到 ~3e-5 後 plateau,不是指數爆炸;loss 曲線重疊。

**影響**:訓練期不能開這個 flag(會算錯,不只是不可重現)。推論期可以開。
剝掉 `salt_core` 的最小 repro 還沒 bisect 出來;⚠️ 決定擱置——硬體 bit-exact 驗證比對的是
forward,不需要動這個。

### §1.5 firing-rate 目標帶選出的 init_k 反而訓練較差(問題紀錄第十二節)— ✅ 已解決(2026-09-08)

**準則定案**:廢棄 firing-rate 目標帶準則,`init_k` 三層寫死 `5.0`(committed config 值,不校準)。
完整推導 + 數值驗證 V1–V6 見 `docs/math/初始權重尺度推導.md`:膜電位穩態變異數
$\sigma_V \propto \text{init\_k}$ → 命中 firing-rate 帶 $[0.2,0.5]$ 必然把 $\sigma_V$ 推到
$\gtrsim v_{th}$(單筆事件觸發區)→ 該區 surrogate 斜率崩 + 資訊塌陷 + 事件爆炸 + init loss 條件差。
V6 實測(10 epoch,同 seed):`init_k` 5 ≈ √3(Lee 變異數保持)≈ 0.80 > 8/8 ≈ 0.765 > 8/64 ≈ 0.735。

**跟架構的關係**:「調整初始尺度直到某個 per-layer 診斷命中目標」這個**能力**留在核心
(`salt_core/calibrate.py` 的 `calibrate_init_scale`,準則無關),給未來全新架構用;
conv baseline 不再呼叫。`ConvLayer.calibration_measure`(firing-rate measure)留著但不再是選值依據。
`configs/conv/compressed_baseline.yaml` 已改成 `init_k` 全 5.0(舊 8/64 版刪除)。

**留下的開放題(串更大網路時再討論,不擋現在)**:`init_k = √3`(Lee 變異數保持)+ ReDo
作為一個 package。√3 冷、壓縮佇列記憶體優勢隨網路深度複利(V6:conv2 `L` √3→513
vs `init_k=5`→974),與 FPGA spike 稀疏目標同方向;但 √3 之下隱藏層(尤其 fan-in 大的
FC→FC)init 幾乎全休眠,需要 ReDo 持續回收才撐得起。目前 2-conv baseline 用 `init_k=5`、
不做 ReDo;dormant-score 紀錄(`src/dormant.py`,寫進 metrics.csv)先跑著累積資料。
詳見 `docs/math/初始權重尺度推導.md` 步驟 8.4 / 10。

### §1.6 緩解手段不該焊進通用訓練迴圈(問題紀錄第十節尾)— ✅ 已解決

現行 `train_conv_compressed.py` 的 `loss_fn` 是純 softmax cross-entropy,沒有 firing-rate
regularization / threshold annealing 焊進去;`firing_rate` 只當 metrics.csv 的哨兵指標。
翻修規劃 step 5 的解碼器模式落實了「訓練迴圈向解碼器要『拿去算 loss 的東西』」,
真要加緩解手段,走解碼器 / layer hook,不動通用迴圈。
