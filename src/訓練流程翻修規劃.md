## 1. 原始問題清單

### A. 控制流:三件事纏在同一個 `train()` 裡

`train()` 曾同時是:

1. **普通訓練迴圈**:每 epoch 洗牌 → 每 batch 算 loss+梯度、更新 → 隔一陣子 val 評估、寫一行 log、存進度。
2. **自動長大 + 重編譯**:壓縮版 conv 佇列是固定大小緩衝（`L` / `max_out_spikes`），某 batch 真實需求超過 → 這 batch 作廢 → 該層緩衝 `grown_to_fit` → 整個 train step 重編譯 → 從最近的 checkpoint 接回去。
3. **checkpoint 存讀**:`_save_checkpoint` / `_load_checkpoint` 知道 optax 內部 pytree 長怎樣、跟 `while` 迴圈的「重編譯就重載」纏在一起。

症狀:`have_checkpoint` / `overflowed` / `start_epoch` 共用可變狀態穿過整個迴圈;三層
`break`;`last_checkpoint_epoch` 只為一句 log 字串存在;`if best_params is None` 的初始化塞在重編譯分支裡。

### B. config 存取

- `train()` 自己 `load_config(path)` → 不能拿「已載入 / 已改過的 dict」乾淨呼叫（測試只好繞路寫 yaml 檔）。
- `cfg["model"]` inline 取五六處;沒有「解析在一處」這一步。
- `cfg` 同時是**輸入 spec** 跟**輸出暫存本**:`cfg["best_val_accuracy"]` / `cfg[f"final_{name}_L"]` / `cfg["model"]["resolved_init_k_*"]` 一路塞,最後整個 dump 成該次 run 的 `config.yaml`。輸入跟結果混在同一個 dict。

### C. 訓練紀錄 / logging

- 五個平行的 per-epoch 累加器:`epoch_losses` / `epoch_firing_rates` / `epoch_grad_norms` / `epoch_dec_metrics` / `epoch_obs`。
- `row = {...}` inline 組 ~20 行;週期性 `print(...)` 再從 `row` 重推字串 ~10 行;`_write_experiment` 又自己跑一輪結尾 `print` + 寫 5 個檔。
- 沒有一個東西負責「每個 epoch 記什麼」「結束寫什麼」→ 需要一個 recorder。

### D. run 紀錄不完整 / 分散

- commit hash 在獨立的 `git_commit.txt`,不在任何一份主紀錄裡。
- run 紀錄散成 `config.yaml`（輸入+結果混）+ `git_commit.txt` + `metrics.csv` + `params.npz` + `best_params.npz`,沒有一份完整、write-once 的「這次跑了什麼」。

### E. 策略 vs 參數的邊界（現況釐清,不是要改的東西）

- 目前**只有一支 trainer**,「用哪套策略」沒寫進 config——就是這支腳本在某個 commit 當下做的事。策略變 = 改腳本 = 一個 commit → 靠 run 紀錄裡的 `git_commit` 釘住。參數變 = 改 yaml → 靠 config 快照釘住。
- 邊界現在不全乾淨:有些策略性旋鈕（`L_grow_factor` / `out_grow_factor` / `decoder`）在 model yaml 裡當參數。翻修**不搬**,只是知道它們算「腳本開放出來讓人調的策略參數」。
- 哪天真的有第二支 trainer,commit hash 不夠,那時 config 要多一個 `train.trainer: xxx` 指名。現在一支,不需要。

### F. 其他小的

- entrypoint 環境 boilerplate（盤點 §5.3）——`conv_param_search.py` 刪掉後只剩這一支 entrypoint,沒有共用對象,**低優先 / 先不動**。
- `zip(x._fields, x)` 的 npz 存讀慣例（盤點 §5.4）——`params` 變成位置 tuple 後已改成 positional / `layer.name`,處理掉了。
