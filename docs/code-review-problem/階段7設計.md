## 目標

- FC 是普通 layer:有輸出容量、掃描步數容量,出界會被 `fits` 抓到、走同一套放大縮小。
- 掃描步數的容量旋鈕 conv、FC 統一成「額外步數」(見下一節)。
- `build_network` 能組 FC 接 FC;conv 接在 FC 後面在 builder 就擋。
- dormant 統計哪些層由 config 決定。
- 數值不變:黃金輸出 `compare`、`compare_quant` 0 筆不同;訓練只有放大縮小的時間點變。

## 掃描步數旋鈕改成「額外步數」

浮點版一層的迴圈:每步最多吃 `chunk_size` 筆**輸入**事件,這層有神經元 fire 時那一步停在 fire 那筆。
步數上界公式不改:m* = min(b>0 的筆數, floor(Σ正的 b / v_th)),上界 = m* + ceil((L − m*) / chunk_size),
L 是這層的佇列長度(conv 是 `max_queue_len`,FC 是輸入流長度 = 上一層的 `max_out_spikes`)。

- 迴圈步數 = 基本步數 ceil(L / chunk_size) + `max_extra_steps`。
- 需求 = 上界 − 基本步數。不 fire(例如輸出層 v_th=1e9)或 `chunk_size`=1 時需求是 0。
- 例:L=10、chunk_size=5、在輸入 0、5 fire,每步吃 1、5、4 筆,要 3 步;基本步數 2,實際多 1 步。

為什麼不用總步數:FC 的 L 是上一層的旋鈕。總步數裡含 ceil(L / chunk_size),上一層放大時 FC 存的總步數
就過時;出界那次 FC 的需求是用舊 L 算的看不出來,要等重編譯、重跑才發現,多一次退回跟重編譯。
基本步數在編譯時從陣列長度現算,跟上一層那次重編譯一起更新。
例:上一層 3417 → 5126、chunk_size=1024,總步數要 4 → 6(多重來一次);額外步數一直是 0。

conv 一起改,兩種層同一個定義。佇列放大時的特例保留:這批的需求是在裝不下的佇列上算的,不可信,
額外步數設成「一定夠」的 新 L − ceil(新 L / chunk_size),總步數等於新 L,跟現在一樣。

## 決定(2026-09-28)

| 決定 | 結果 |
|---|---|
| 掃描步數旋鈕 | conv、FC 都改成「額外步數」`max_extra_steps`(原本第 2b 條寫「跟 conv 一樣的 `max_steps`」) |
| dormant 統計哪些層 | config `train.dormant_layers` 列層名,沒填不統計 |
| 分幾步 | 7.1(旋鈕改定義、舊實驗轉換)、7.2(FC 容量跟其餘)分開 |

理由:

- 額外步數:FC 的基本步數跟著上一層容量變,存總步數會過時,上一層放大時多一次退回跟重編譯;
  沒填時 0 等於現在的行為。conv 一起改是為了兩種層同一個定義。
- dormant 用 config:輸出層不一定是膜電位回歸,頻率編碼的輸出層也會有 dormant;挑哪些層是應用決策,
  不從層的型別或位置推。
- 分兩步:7.1 改 conv 的既有行為又要轉舊實驗,單獨驗證才看得出問題在哪一步。
