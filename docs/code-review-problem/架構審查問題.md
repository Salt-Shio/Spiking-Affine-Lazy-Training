## 1. 評估路徑不看容量出界

**位置**:

- `example/utils.py` 的 `make_evaluate`:內部取 `apply_batched` 結果時,
  每層的診斷直接丟掉。
- `salt_core/dormant.py` 的 `dormant_report`:同樣不看診斷。

**檢查方式**:讀 `make_evaluate` 內部的 jit 函式,跟 `run_epochs` 裡容量放大
只在訓練 batch 上觸發的那段。

**結論**:

- `L`、`max_out_spikes`、`max_steps` 三個容量只照**訓練資料**長大。
- val/test 樣本如果需要更大的容量:
  - 壓縮佇列放不下的候選事件被丟掉。
  - 掃描步數不夠時,後面的事件沒被處理。
  - 輸出 spike 超過上限時被截掉。
- 三種情況都不會報錯,準確率照樣算得出來。
- 受影響的地方:
  - 訓練中挑 best params 用的 val accuracy。
  - `eval_test.py` 的 test accuracy。
  - 每個 epoch 的 dormant 統計。探測樣本是訓練集的前 128 筆,不是 val。
    這些樣本訓練時檢查過容量,但用的是當時的權重;換成 epoch 結束時的權重,
    跟權重有關的容量(輸出 spike 數、掃描步數、conv2 的佇列長度)仍可能出界。
- 92.75% 那次 run 的 val:**沒有踩到**(階段 0c 實測,2026-09-27)。
  - 2000 筆逐筆比容量診斷跟上限,三種容量都沒出界,準確率剛好 92.75%,
    這個 baseline 可信。
  - conv1 的佇列很緊:需要 181、上限 185。
  - test set(`eval_test.py`)跟 dormant 的探測樣本沒查,修正仍然要做。

**處理**:

- 出界政策(2026-09-27 定):**放大評估用的容量,出界的那批重算**。
  - 另外兩個選項不採用:直接 raise 會讓長時間訓練在後期中斷;只標記不可信,
    挑 best params 時還是用錯的數字。
  - 評估只跑 forward、不更新權重,不需要退回 checkpoint,重算那一批就好。
    三個容量都有「需要多大」的診斷值,放大公式沿用訓練的。
  - 評估用自己的一份容量,放大不影響訓練的容量。
  - 重算過幾次記進 `metrics.csv`(`eval_test.py` 記進 `eval/<which>.yaml`)。
  - 適用範圍:訓練中的 val 評估、`eval_test.py`、dormant 統計。
  - 整數版(量化模擬)不在這次範圍:它的診斷只回報有沒有截斷、不知道要多大,
    暫時維持現在的標記做法,階段 5 再一起處理。
- 92.75% 那次的 val 沒有踩到,由 0c 回答(見上面結論)。

**職責對調角度**(總覽 B8):

- 正確性防護全靠呼叫端記得檢查診斷,等於把框架的責任推給使用者。
- 處理時一併考慮讓 forward 結果自己帶「有效」旗標,不要只修
  `make_evaluate` 一處,不然下一個呼叫端又會漏掉。

## 2. `FCLayer` 要能多層串接,目前只能當輸出層

**定案(2026-09-27)**:FC 是普通 layer,要能當隱藏層、FC 接 FC 多層串接。
原本另一個方案「明講 FC 只能當輸出層」不採用。

**位置**:

- `salt_core/layers.py` 的 `FCLayer`。
- `example/models/conv_net.py` 的 `build_network`。

**已經支援的部分**:

- 底層 primitive 已經測過 FC 接 FC 多層串接,含 fire 跟跨層梯度:
  `test_multi_layer_forward.py`、`test_multi_layer_random_gradient.py`。
  這些測試直接呼叫佇列建構 + 掃描 + 抽輸出事件流,掃描步數給整條佇列長度。
- 缺的是 `FCLayer` 物件、`build_network`、訓練迴圈這幾層。現有用到
  `FCLayer` 的測試,全部只把它當最後一層。

### 2a. 輸出容量寫死成 `n_out`

- `_run_forward`、`_run_forward_quantized` 抽輸出事件流時,輸出上限是 `n_out`。
- `salt_core/layer_chain.py` 的 `_select_spikes`:真 spike 數是整個
  spike_mask 的總和,沒被上限截掉。
- 所以 FC 當隱藏層時:
  - 每顆神經元可以 fire 很多次,整層 spike 總數一超過 `n_out`,多的就被截掉。
  - `grown_to_fit` 永遠回傳自己,容量不會長大。
  - 被截掉的是**神經元編號大的** spike,不是時間晚的:取 spike 時先依神經元
    順序取滿上限,之後才依時間排序。
  - 輸出事件流標記的真事件數會大於陣列實際長度,下游拿到的事件不完整。
- **處理**:FC 加輸出容量,跟 conv 走同一套放大/縮小機制。整數版的
  `output_truncated` 改成跟這個容量比。
- **階段 5.2b 之後**(2026-09-27,使用者確認):`LayerDiagInt` 刪掉,量化版改回傳
  `LayerDiag`、用 `capacity.fits` 判斷出界。FC 的 `capacity` 是 `None`,所以量化版也跟
  浮點版一樣不再檢查 FC 輸出出界(目前唯一的 FC 是不 fire 的輸出層,沒有實際影響)。
  FC 加輸出容量之後,兩個 backend 一起恢復這個檢查。

### 2b. 掃描步數假設 FC 不會 fire

- 掃描步數是「輸入流長度 ÷ `chunk_size`」取上界。
- 這只在不 fire 時才夠:
  - 不 fire 的一步,吃掉整個 chunk。
  - 有 fire 的一步,只吃到 fire 那筆為止。
- 反例(讀掃描程式碼推得,沒實測):10 筆事件、`chunk_size=5`,掃描只跑 2 步。
  - 第 1 步:第 0 筆就 fire,只吃掉 1 筆。
  - 第 2 步:從第 1 筆開始,第 5 筆 fire,吃到第 5 筆為止。
  - 第 6~9 筆沒被處理,不會報錯。
- `chunk_size=1` 時步數等於輸入流長度,沒有這個問題。
- FC 的 `LayerDiag` 已經算了掃描步數上界 `min_steps_needed`,只是沒人用。
- **處理**:FC 也有 `max_steps` 容量,跟 conv 一樣用這個上界做出界放大。

### 2c. `build_network` 接完 FC 沒更新幾何

- conv 分支會把下一層的輸入幾何更新成這層的輸出;FC 分支沒有。
- 後果:
  - FC 接 FC:第二個 FC 的 `n_in` 會是「FC 之前那個 conv 的攤平大小」,
    不是前一個 FC 的 `n_out`。
  - conv 接在 FC 後面:拿到的是 FC 之前的舊幾何。
- **處理**:
  - FC 之後,下一層的輸入大小 = 這個 FC 的 `n_out`。
  - conv 接在 FC 後面沒有空間幾何可用,建網路時直接擋掉(2026-09-27 定)。
  - 第 18 條的串接檢查也要涵蓋 FC。

### 2d. 第一層是 FC 會壞(定案,2026-09-27:支援第一層是 FC)

- 原始事件轉輸入流時讀第一層的 `h_in`/`w_in`,`FCLayer` 沒有這兩個欄位。
- 原始事件攤平後的編號(channel、y、x 的順序)剛好就是 FC 的輸入 index,
  只有轉換入口要改。
- 依賴第 6、17 條:輸入網格由網路容器管,不讀第一層的欄位。

### 2e. 預設 `v_th=1e9`

- 預設值的理由寫的是「FC 目前只當輸出層」(總覽 A2),是把應用假設寫進
  框架預設值。
- **處理**:改成跟 conv 同一個預設值(1.0)。FC 是普通 layer,預設值跟 conv 一致。
- 影響範圍:
  - 所有 config 的 FC 都明寫了 `v_th: 1.0e+9`,不受影響。
  - 靠預設值的只有三個測試:`test_monitor.py`、`test_dormant.py`、
    `test_quantize.py`,要補明寫。

### 2f. 下游只處理 conv 的容量

- 印放大訊息、`metrics.csv` 的容量欄位、`run.yaml` 的 `final_capacity`、
  `rebuild_layers`、replay 的 `chunk_size=1` 覆蓋、dormant,全部用
  `isinstance(layer, ConvLayer)` 挑層。
- FC 有容量之後,不要在每一處再加一個 FC 分支。用第 5 條的容量型別統一
  處理(第 20~22 條同理)。

### 2g. 測試

- `FCLayer` 物件層級的多層串接:conv → FC(會 fire)→ FC(輸出)走
  `run_network`,結果跟 primitive 逐層呼叫一致。
- 2b 的反例:有 fire、`chunk_size>1` 時,每筆事件都有被處理。
- `build_network` 的 FC 接 FC:第二個 FC 的 `n_in` 等於前一個 FC 的 `n_out`。

**依賴**:2a、2b、2f 依賴第 5 條的容量型別;2d 依賴第 6、17 條。

### 3b. 「浮點模型 → 硬體參數」只存在 notebook

### 3c. 整數路徑借用浮點的佇列建構器

**位置**:`salt_core/layers.py` 的 `_run_quantized_scan`。

- 整數權重碼先丟進浮點的佇列建構器,變成 float32 的 `AffineMap.b`

- 目前能正確運作(|q| < 2^24 時 float32 精確),但兩條路徑綁在浮點的
  中間表示上。

### 3d. 量化準確率用 Python 迴圈逐筆跑

- 之後包進 jit 時要注意:`quantize.apply_decay_table_int` 的入口檢查在
  jit 裡會直接跳過(docstring 有寫)。

**處理**:

## 4. `layers.py` 的執行模式 × 軌跡組合爆炸

**位置**:`salt_core/layers.py`、`salt_core/dormant.py`。

**現況**:

- 每個層類別 4 個公開 forward:
  `forward`、`forward_traced`、`forward_quantized`、`forward_quantized_traced`,
  外加 2 個私有共用內核。
- 網路層級 4 個變體:
  `run_network`、`run_network_traced`、`run_network_quantized`、
  `run_network_quantized_traced`。
- `dormant.py` 的 `_per_neuron_activity` 自己又抄了一份逐層迴圈,
  而且用 `isinstance(layer, ConvLayer)` 挑層。同一個迴圈總共 5 份。
- 四種 forward 的回傳 tuple 長度不一樣(2、3、3、4 個元素)。

**問題**:再加一種模式(例如 QAT 用的 fake-quant、剪枝),每個層類別、每個
`run_network` 都要各加一套。

**處理**:

- 層只負責兩件事:建佇列、從結果吐出下一條事件流。
- 「怎麼掃描」抽成 backend:浮點 surrogate、整數定點。
- 「要記錄什麼」變成參數(最後結果 / 逐步軌跡 / 逐神經元活動量)。
- 網路層級只留一支 `run_network`,吃 backend 跟記錄選項。
- dormant 的逐層活動量改成用這支 `run_network` 的記錄選項拿。

**職責對調角度**(總覽 A3、A4):

- dormant 只收 conv 層,是依「FC 目前是不 fire 的輸出層」做的應用決策。
- `dormant_report` 自己吃原始事件 tuple、自己 jit、自己分批 vmap,是使用者
  程式的評估迴圈。
- `salt_core` 只留純歸約的 `dormant_score`,加上 `run_network` 的逐神經元
  活動量記錄選項;挑哪幾層、跑哪批探測樣本的迴圈搬到 `example`。

## 5. 「容量」沒有自己的型別

**位置**:`salt_core/layers.py` 的 `ConvLayer`,以及所有讀容量的地方。

**檢查方式**:在 `salt_core/`、`example/` grep
`isinstance(.*ConvLayer)`,排除測試。

**結論**:

- 容量的值(`L`、`max_out_spikes`、`max_steps`)、放大/縮小的倍率跟門檻、
  放大縮小的策略,全部塞在 `ConvLayer` 裡。
- 測試以外有 **11 處** `isinstance(layer, ConvLayer)`:
  - `example/train_conv_compressed.py` 3 處
  - `example/metrics_log.py` 4 處
  - `example/utils.py`、`example/replay_epoch.py` 各 1 處
  - `example/analysis/inspect_explosion_batch.py` 1 處
  - `salt_core/dormant.py` 1 處
- `Layer` 協定逼 `FCLayer` 實作三個什麼都不做的方法
  (`grown_to_fit`、`shrink_max_steps`、`shrink_max_out_spikes`)。
- `example/checkpoint.py` 不存容量,類別說明自己也寫了「沒有跨行程
  resume」。跑好幾小時的訓練中途掛掉,沒辦法接著跑。

**處理**:

- 抽一個容量值型別,層提供一個「容量」屬性,沒有容量的層回傳 `None`。
- 放大/縮小策略(倍率、門檻、防震盪規則)搬到 `example/` 的容量控制器。
- checkpoint 一起存容量,支援跨行程 resume。
- 上面 11 處 `isinstance` 改成讀容量屬性。
- 第 2 條定案後 FC 也會有容量(輸出容量、`max_steps`,沒有壓縮佇列 `L`),
  容量型別要能同時描述 conv 跟 FC 兩種組合,上面三個方法對 FC 也不再是空的。

**職責對調角度**(總覽 A1):

- 放大/縮小策略放在層裡,等於把 LR scheduler 塞進 `nn.Conv2d`。
- 策略元件放 `salt_core`(像 `torch.optim.lr_scheduler`)或 `example` 都可以,
  重點是不能在層裡。
- 第 20~22 條都依賴這條的容量型別。

## 30. docstring 跟註解寫成長篇文章,還用 markdown

**使用者意見(2026-09-27)**:docstring 跟註解寫成這樣沒有人看得懂,還用 markdown。
**定案要改**。下面的寫法規則 2026-09-27 定案,測試檔另外放寬一條。

**檢查方式**:統計非測試程式碼的實體行數(不含空行),每一行歸成一類:

- 在 docstring 裡 → docstring。
- 有任何程式碼(包含行尾帶註解的程式碼行)→ 程式碼。
- 只有註解 → 註解。

**結論**:

- 整體說明文字佔 40%~44%,依納入的檔案範圍而定。
  - 用 `salt_core/`、`example/`、`data/src/`、`viz/` 的範圍:程式碼 2395 行、
    docstring 1576 行、註解 277 行,佔 44%。
  - 另一個 agent 複核時用的範圍算出 40%。
  - (初版寫 51%,統計腳本有 bug:行尾帶註解的程式碼行被算成註解,docstring
    裡的空行被扣了兩次。)
- `salt_core` 核心檔案的說明文字比程式碼還多(兩邊複核的數字一致):

| 檔案 | 說明文字佔比 |
|---|---|
| `connectivity/fc.py` | 65% |
| `layer_chain.py` | 61% |
| `connectivity/conv.py` | 57% |
| `monitor.py` | 56% |
| `quantize.py` | 56% |
| `core.py` | 55% |
| `chunk_scan.py` | 54% |

- 具體症狀:
  - **太長**:`run_layer_forward` 的 docstring 56 行,函式本體只有 2 行;
    `_compress_candidates` 50 行;`build_fc_queue` 28 行,程式碼才 12 行。
  - **寫成推導跟辯論**:docstring 裡放公式推導、否決過的做法,還有「不是…而是…」
    「不要…否則…」這種跟 reviewer 爭論的語氣。
  - **同一個理由到處重寫**:「為什麼要帶 s_spike 當下一層的 event_gain」在
    `fc.py`、`conv.py`、`layer_chain.py`、`chunk_scan.py` 四處各寫一大段,
    `docs/問題紀錄.md` 第四節也有。
  - **markdown**:反引號約 1300 對、粗體約 50 處、LaTeX 公式約 60 處(大部分在
    `quantize.py`)。LaTeX 在原始碼裡還要跳脫反斜線,例如 `\\tilde V`,不管在原始碼
    還是編輯器的滑鼠提示裡都讀不出來。
  - **引用文件章節編號**:「推導文件第 4.3、4.4 節」「§12」之類,讀者要開另一個
    檔案才看得懂,文件編號一改就失效。
  - **歷史跟除錯經過**:已列在第 9 條。

**寫法規則(定案)**:

- docstring 只回答三件事:
  - 做什麼:一句話。
  - 參數跟回傳:形狀、單位、限制。
  - 什麼情況會 raise。
- docstring 超過大約 10 行,代表那些內容屬於 `docs/`,不屬於程式碼。
- 註解只寫「程式碼本身看不出來的原因」,一到兩行。
- 不寫進程式碼的東西:
  - 推導 → `docs/math/`。
  - 決策、否決過的做法 → `docs/問題紀錄.md`。
  - 歷史、除錯經過 → git。
- 不用 markdown:不用反引號、粗體、LaTeX。公式寫純文字,例如
  a = (1 - 1/tau) ** dt。
- 同一個設計理由只寫一次,寫在 `docs/`。程式碼裡最多留一句「理由見
  docs/某文件」,不寫章節編號;要指到某一節時寫章節標題。
- 測試檔放寬一條:「預期答案怎麼算出來」(手算過程)可以留在測試裡,用純文字寫。
  其他規則照舊,歷史、辯論、除錯經過、校準經過一樣拿掉。理由:手算過程就是
  斷言的答案來源,跟斷言放在一起才看得出答案對不對。

**範例**:`build_fc_queue` 的 docstring,28 行改成大約 10 行:

```
"""FC 層的事件佇列:每顆輸出神經元一列仿射映射。

event_times: (S,) 已排序的事件時間,整數 ms。
event_source_idx: (S,) 每筆事件的來源神經元,對應 W 的欄。
W: (n_out, n_in) 權重。
tau: 衰減時間常數。
n_real_events: 前幾筆是真事件,其餘位置變成不作用的映射(a=1, b=0, dt=0)。
event_gain: (S,) 乘進權重的增益。接在上一層後面時傳上一層的 s_spike,
    理由見 docs/問題紀錄.md。None 等於全 1。

回傳 FCQueue:maps 跟 delta_t 的形狀都是 (n_out, S)。
"""
```

**處理**:

- 第 3~7 條重寫的程式碼直接照規則寫,不要寫完再改一次。
- 既有檔案逐檔改寫,跟第 9 條一起做。
- 要刪掉的推導或理由,先確認 `docs/` 裡已經有;沒有就先搬過去,不要直接丟。
- 規則放進 repo 有追蹤的 docs 文件,專案 CLAUDE.md 放一行指過去
  (2026-09-27 定)。專案 CLAUDE.md 被 `.gitignore` 排除,只寫在那裡的話,
  規則不會跟著 repo 走。

## salt_core / example 職責對調(總覽)

**判準**:`salt_core` 相當於 PyTorch,`example` 相當於使用 PyTorch 的程式。

- 框架不該替使用者做應用決策:網路長相、訓練策略、評估迴圈。
- 使用者不該需要懂框架的內部約定才用得對:記憶體排列、不變量、
  診斷欄位的語意。

**檢查方式**:

- grep `salt_core` 非測試程式碼的 import:沒有任何一行 import
  `example`/`data`/`viz`。**import 方向是對的**。
- 對調發生在職責跟知識的層面,靠逐檔讀 `salt_core/`、`example/` 判斷。

### A. 應用決策寫死在 salt_core

| 代號 | 內容 | PyTorch 類比 | 條目 |
|---|---|---|---|
| A1 | 容量的放大/縮小策略是 `ConvLayer` 的欄位跟方法 | LR scheduler 塞進 `nn.Conv2d` | 5 |
| A2 | `FCLayer` 預設 `v_th=1e9`、輸出上限 `n_out`,理由是「目前只當輸出層」 | `nn.Linear` 預設自己是最後一層 | 2 |
| A3 | dormant 只收 `ConvLayer`,理由是「FC 不 fire」 | 框架依你的網路長相挑層 | 4 |
| A4 | `dormant_report` 自己跑評估迴圈 | torch 內建固定 probe batch 的評估迴圈 | 4 |
| A5 | 只服務 `example` 驗證腳本的量測函式 | — | 11 |
| A6 | docstring 用 `example` 的用法定義契約 | 文件寫「本函式只給 my_train.py 用」 | 23 |

### B. 框架約定由 example 扛著

| 代號 | 內容 | PyTorch 類比 | 條目 |
|---|---|---|---|
| B1 | 網路容器:逐層初始化、原始事件轉輸入流、batch vmap | `nn.Sequential` 要自己寫 | 17 |
| B2 | 層串接相容性檢查 | 接錯 channel 不報錯 | 18 |
| B3 | `LayerDiag` 跨 batch 的歸約規則 | 使用者自己判斷每個診斷欄位用 mean 還是 max | 19 |
| B4 | 診斷欄位 ↔ 容量旋鈕的對照 | — | 20 |
| B5 | 層的序列化 | `state_dict` 要自己拼 | 21 |
| B6 | `chunk_size=1` 的 `max_steps` 不變量 | 改 stride 要自己同步改 padding | 22 |
| B7 | 神經元攤平順序 | 要懂 tensor 的內部記憶體排列 | 3 |
| B8 | 容量出界的正確性防護 | op 會因為使用者忘了看旗標就默默截資料 | 1 |

## 17. `salt_core` 沒有網路容器

**位置**:`example/models/conv_net.py` 的 `ConvNetCompressed`。

**結論**:

- 它做的事:
  - 逐層分 key 初始化權重。
  - 把原始事件轉成第一層的輸入流(要用第一層的 `h_in`/`w_in`)。
  - `vmap` 成 batch 版。
- 這些都不依賴 N-MNIST。這個檔案裡唯一跟資料集有關的,是
  `build_decoder` 用的類別數。
- `salt_core` 只提供 `run_network` 這一支函式,沒有「一列層 + 權重初始化
  + 輸入轉換」的容器,每個使用者都要自己寫一份。notebook 跟
  `replay_epoch.py` 也各自重寫了原始事件轉輸入流那一段(見第 6 條)。

**處理**:

- `salt_core` 提供網路容器,收 init / apply / batch apply / 原始事件轉輸入流。
- 跟第 4 條統一後的 `run_network` 一起設計。
- `example/models/` 只留 `build_network`(yaml → 層參數)跟 `build_decoder`。

## 18. 層串接相容性只在 `example` 推導,`salt_core` 不檢查

**位置**:

- `example/models/conv_net.py` 的 `build_network`。
- `salt_core/layers.py` 的 `run_network`、`ConvLayer`。

**檢查方式**:

- grep `salt_core` 非測試程式碼:沒有任何地方比對上一層輸出跟下一層
  輸入的幾何。
- `ConvLayer` 類別說明寫「組層 list 的時候 Python 層級檢查一次(就是
  PyTorch 要你自己對齊 channel 的那個檢查)」,但這個檢查只以「從 config
  推導」的形式存在於 `build_network`。
- **沒有實際跑過接錯的網路**。下面的「靜默算錯」是讀程式碼,加上 JAX
  越界 gather 會把 index 夾住、不報錯的行為推得的。

**結論**:

- `ic`、`h_in`/`w_in`、FC 的 `n_in` 只要跟上一層對不上:
  - 扁平編號還原成座標時用了錯的 `h_in`/`w_in`,座標整個錯位。
  - 用超出範圍的 channel/神經元編號去取權重,JAX 會夾到邊界,拿到別的權重。
  - 兩種情況都不會報錯。
- PyTorch 接錯 channel 會直接 shape error;這裡是靜默算錯。
- 走 yaml → `build_network` 的路徑,幾何是推導出來的,不會接錯。
  手動組層(notebook、測試、之後別的模型)完全沒有保護。
- `docs/架構.md` 的「組網路」一節寫 `build_network` 在 `layers.py`,原本的
  設計意圖應該是放在框架(見第 15 條)。

**處理**:

- `salt_core` 在組網路時檢查相鄰兩層的幾何,不合就 raise。放在第 17 條的
  容器建構時,或 `run_network` 入口(層是靜態 Python 物件,trace 期檢查
  沒有執行成本)。
- `build_network` 保留「從 config 推導幾何」的便利功能,但對不對以框架的
  檢查為準。

## 19. `LayerDiag` 跨 batch 的歸約規則寫在 `example`

**位置**:`example/train_conv_compressed.py` 的 `make_train_step` 裡的 `loss_fn`。

**結論**:

- 每個欄位跨 batch 怎麼歸約,寫在 `example`:
  - `spike_count`、`firing_rate`:取平均,記錄用。
  - `max_real_queue`、`n_out_spikes`、`min_steps_needed`:取最大,出界偵測用。
- 這是 `LayerDiag` 每個欄位本身的語意,不是訓練腳本的選擇。
- `LayerDiag` 新增欄位時,`example` 要知道該用哪一種歸約。用錯(例如
  容量訊號取平均)放大機制就失效,而且不會報錯。

**處理**:`salt_core` 在 `LayerDiag` 旁邊提供跨 batch 歸約,每個欄位的
規則跟欄位定義放在一起。`example` 直接呼叫。

## 20. 「診斷欄位 ↔ 容量旋鈕」對照在 `example` 重寫好幾次

**結論**:

- 對照關係:
  - `max_real_queue` ↔ `L`
  - `n_out_spikes` ↔ `max_out_spikes`

## 21. 層的序列化由 `example` 拼湊

**位置**:

- `example/utils.py` 的 `rebuild_layers`、`save_params_npz`/`load_params_npz`。

**結論**:

### 21a. replay 用 run 結束時的容量重跑中途的 epoch

(2026-09-27 另一個 agent 複核時發現)

- `example/replay_epoch.py` 重建層時,用的是 **run 結束時**的容量
  (`run.yaml` 的 `final_capacity`),拿來重跑任何一個 epoch 的權重快照。
- `max_out_spikes` 在訓練中途會縮小。重跑較早的 epoch 時,輸出 spike 可能超過
  run 結束時的上限而被截掉。
- replay 走的是記錄逐步軌跡的 forward,這條路不回傳診斷,截掉了也不會有提示。
- `analysis/inspect_explosion_batch.py` 已經發現這個問題,改成讀 `metrics.csv`

  - conv2 的 `max_steps` 在 epoch 11 從 1083 縮到 540,但 replay 會把
    `max_steps` 補到 `L`。
- 這是還沒發生、但隨時可能發生的問題。

**處理**:

- `salt_core` 提供層清單的序列化(幾何 + 動力學 + 容量)跟權重存讀。
- `run.yaml`、checkpoint、`eval_test.py`、`replay_epoch.py` 都改用它,
  不再拼 config + 補欄位。
- 序列化要能還原**每個 epoch 當下**的容量:逐 epoch 記容量,或權重快照直接
  連容量一起存。replay 跟 `inspect_explosion_batch.py` 都改用這份資料。

## 22. 「`chunk_size=1` 時 `max_steps=L`」這個不變量寫在 `example`

**處理**:層提供「換 `chunk_size`」的方法,由層自己維持這個不變量。

## 24. `test_train_conv_compressed.py` 的完整訓練大約一半是重複的

## 26. 出界測試綁真實資料、校準數字、解析印出的中文訊息

**位置**:`example/tests/test_train_conv_compressed.py` 的出界系列。

**結論**:

- 要命中「第一個 batch 出界」「存過 checkpoint 之後才出界」「最後一個 epoch
  才出界」這些邊界,靠的是實際跑出來的校準數字,例如「seed=1 時 epoch1 第 2 個
  batch 的 conv2 佇列需求大約 1016」。
  - 資料載入、初始化、動力學只要一改,就可能挑不到原本的邊界。
  - 測試會因為跟被測機制無關的原因失敗。
- 放大了什麼,只能用正規表示式從印出來的 `[出界]` 中文訊息解析。訊息格式一改,
  測試就壞。
- 根本原因在 `train()`:
  - 在內部自己建資料集,測試沒辦法換成合成資料。
  - 放大事件只印出來,沒有結構化回傳。

**處理**(拆訓練腳本時一起做,見第 7 條):

- 資料可以從外面傳進去。出界測試改用合成的小資料,直接控制每個 batch 的
  事件數,精準命中邊界。
- 放大/縮小事件結構化記錄(回傳或寫進 run 紀錄),測試斷言結構化資料,
  不解析訊息。
