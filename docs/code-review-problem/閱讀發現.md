## 1. conv 佇列剛好裝滿時沒有 catch-up 欄

**位置**:`salt_core/connectivity/conv.py` 的 `_delta_t_three_regimes`(catch-up 放在第 n 欄，n 是這個位置的真事件數);出界判斷在 `salt_core/layers/conv.py` 的 `needed["max_queue_len"]`(取 n 的最大值，n ≤ max_queue_len 就算放得下)。

**問題**

- catch-up 欄的作用：每個位置的 Δt 加總要等於 T(全域最後一筆真事件的時間),膜電位才會停在同一個時刻 T。
- catch-up 放在第 n 欄，但佇列只有 max_queue_len 欄。n = max_queue_len 時沒有位置放 catch-up,而這時不算出界。
- 結果：這個位置的膜電位停在自己最後一筆事件的時間，不是 T。只有它最後一筆剛好是全域最後一筆時才不受影響。
- 推導文件「conv事件佇列壓縮版推導」的例子裡,n = max_queue_len 的那個位置剛好是這種巧合，所以沒抓到。

**實測**

`build_conv_structure`,k=3、s=2、p=1,輸入 4×4、輸出 2×2,4 筆真事件，時間 [1, 2, 3, 5],T = 5:

| max_queue_len | 各位置 n | 各位置 Δt 加總 |
|---|---|---|
| 3 | [2, 2, 1, 2] | [5, 5, 5, 5] |
| 2 | [2, 2, 1, 2] | [2, 3, 5, 5] |

max_queue_len = 2 時四個位置都放得下，但位置 0、1 的 Δt 加總是 2、3,不是 5。

**影響範圍**

- catch-up 的 b 是 0,只衰減、不會觸發 fire:spike 輸出、下一層的輸入都不受影響。
- 解碼器只讀最後一層 FC 的膜電位,FC 沒有 catch-up:訓練、準確率不受影響。
- 受影響的是 conv 層的最終膜電位。目前讀它的地方:`example/analysis/verify_init_k.py` 的 V3(no-fire 膜電位分布)。
- 整數版照同一份佇列結構跑，一樣受影響。

**可能的處理**

- A. 出界判斷把 catch-up 欄算進需求：需求改成 n 的最大值 + 1。陣列寬度仍等於 max_queue_len;容量需求多 1,現有 config 的起始值可能要跟著調。
- B. 佇列固定多開一欄給 catch-up:容量的意思不變，但陣列寬度變成 max_queue_len + 1,跟容量對不上。
- C. 不修，把限制寫進文件。

建議 A:放得下就保證結果正確，陣列寬度跟容量的對應不變。

**決定**(2026-09-30):A。需求一律是 n 的最大值 + 1(最後一筆剛好是全域最後一筆時也加)。測試的合成資料
(所有事件打在同一個像素)要需求 k 就放 k - 1 筆事件,測試裡寫死的需求數字不動;conv 幾何手算的需求照實加 1。

## 2. 浮點、整數兩邊的掃描命名不對稱

**問題**:同一個角色，兩邊名字各取各的。浮點的結果型別沒有前綴、多了 Forward,函式多了 _forward。

**處理(完成)**:型別兩邊都帶前綴，函式兩邊同名(呼叫時經過模組區分，沒有檔案同時 import 兩邊)。

| 原本 | 改成 | 對照整數版 |
|---|---|---|
| LayerForwardResult | FloatLayerResult | QuantLayerResult |
| ChunkForwardResult | FloatChunkResult | QuantEventResult |
| run_layer_forward | run_layer | run_layer |
| run_layer_forward_traced | run_layer_traced | run_layer_traced |

process_chunk、process_event 不改：浮點一次處理一個 chunk、整數一次一筆事件，本來就不同。歷史文件(問題紀錄、docs/math、架構審查各階段設計)裡的舊名不改。

## 3. 層跟 backend 之間的約定沒有型別

**位置**:`salt_core/backend.py`、`salt_core/float/backend.py`、`salt_core/quant/backend.py`、`salt_core/layers/base.py`。

**關係**:層是主導者，backend 是層用的工具。層呼叫 backend.scan 並把自己傳進去;因為浮點、整數兩個 backend 要的原料不同(仿射映射 vs 整數權重碼跟 Δt),由 backend 回頭呼叫層的方法挑自己要的原料，層不用判斷用的是哪個 backend。

**問題**

- 「backend 要從層讀什麼」只寫在層那邊的 Layer Protocol 跟 backend.py 的一段文字。backend 想標型別就得 import 層，而層為了預設值 backend=FLOAT 已經 import 浮點 backend,形成循環。
- backend.py 開頭用文字列的約定，漏了浮點 backend 用到的 v_th、alpha、chunk_size。(一開始以為整數 backend 用了 tau、weight_shape,查證後只出現在 QuantizedLayerParams 的註解裡,scan 沒用到。)

**處理(完成，2026-09-29)**

- 工具規定自己吃什麼：backend.py 新增 ScanLayer Protocol(backend 要從層讀的屬性跟方法，v_th、alpha、chunk_size、float_values、gather_weight_codes、neuron_delta_t、neuron_n_real、scan_steps)跟 Backend Protocol(scan、readout)。
- 兩個 backend 的 layer 參數標成 ScanLayer,只 import backend.py。
- Layer 繼承 ScanLayer,只另外寫 run_network 要用的東西;補上 quant.convert 用到的 tau。
- structure 在 ScanLayer 裡當不透明型別(backend 不看內容，只轉交);ConvLayer、FCLayer 各自寫實際的結構型別。
- 預設值 backend=FLOAT 留在層上：層是主導者，由它決定沒指定時用哪個工具;層 -> 浮點 backend 是單向，不循環。
- 架構.md 的 backend 一節補上依賴方向。
- 接著補 salt_core 其餘缺的型別標註;巢狀的小函式(scan 的 step、閉包)不補。params、structure 依 backend、層而定的地方寫 Any;numpy、jax 陣列都收的地方用 npt.ArrayLike,同型進同型出的用 ArrayT。
- 驗證:salt_core 242 個測試全過;example、data、viz 137 個測試收集正常(import 沒壞)。

## 4. 物件型別寫成泛用的 NamedTuple、dict、tuple、Any

**問題**:例如一層 forward 裡的 scan.result 標成 NamedTuple,scan.result.spike_mask 看不出是哪個型別的欄位;實際型別只寫在註解裡。

**處理(完成,2026-09-29)**

- backend.py 加三個聯集型別:QueueStructure(conv、FC 的佇列結構)、LayerParams(浮點權重或 QuantizedLayerParams)、LayerResult(FloatLayerResult 或 QuantLayerResult),取代 ScanLayer、Backend、層、網路、解碼器裡的 Any 跟 NamedTuple。
- QuantizedLayerParams 從 quant/backend.py 搬到新檔 quant/params.py:backend.py 要用它，留在 quant/backend.py 會循環 import。
- capacity.py 加 CapacityLayer Protocol(放大縮小時從層讀的東西)跟 LayerT;capacity.py 不能 import 層(層 import capacity)。
- 固定欄位的 dict 回傳改成 TypedDict:DormantScore、TraceSummary、QuantizationError、NetworkDescription。
- 其餘 list、tuple、dict 補上元素型別(Sequence[Layer]、tuple[LayerDiag, ...]、Mapping[str, GrowthPolicy] 等)。
- 留著 Any 的只有 NetworkDescription 每層的欄位 dict:值是 int、float、str、None 混在一起。
- 驗證:salt_core 242 個加 example 3 個測試檔共 256 個測試全過;example、data、viz 137 個測試收集正常。
