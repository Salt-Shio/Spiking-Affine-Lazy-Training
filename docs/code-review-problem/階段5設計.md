# 階段 5 設計:`salt_core` 的層與網路 API

狀態:**定案**(2026-09-27,使用者確認)。三個決定見文末「決定」。

對應 `架構審查問題.md` 第 1(後半)、3(其餘)、4、5、6、17、19、20、21、21a、22 條。

## 目標

- `salt_core` 提供框架該有的東西:容量、執行模式、網路容器、存檔格式。
- `example` 只剩應用決策:網路長相(yaml)、訓練迴圈、評估迴圈、挑哪幾層算 dormant。
- 每一小步都比對兩份黃金輸出:
  - 浮點:預測類別、每層 spike 數相等,`v_final` 容差 1e-4(目前實測誤差 0)。
  - 量化:全部逐值相等。
- 黃金輸出的**資料檔**不動。比對腳本會跟著 API 改,改腳本跟改程式碼放在同一個 commit。

## 新增的檔案

| 檔案 | 內容 |
|---|---|
| `salt_core/capacity.py` | 容量型別、旋鈕 ↔ 診斷欄位對照、`LayerDiag` 跨 batch 歸約、放大縮小公式 |
| `salt_core/network.py` | 網路容器、原始事件型別、唯一的 `run_network` |

## 5.1 容量(第 5、19、20、22 條)

### 旋鈕改名

- `L` 改名 `max_queue_len`(2026-09-27 定)。三個旋鈕統一 `max_` 開頭:
  `max_queue_len`、`max_out_spikes`、`max_steps`。
- yaml 的 key 跟著改。舊 run 裡的 `L` 由 5.4 的轉換處理(見「要決定的事」第 2 點)。

### 診斷改成分組結構(取代「旋鈕 ↔ 欄位」對照表、跨 batch 歸約表)

```python
class LayerDiag(NamedTuple):
    spike_count: jax.Array
    firing_rate: jax.Array
    needed: dict[str, jax.Array]   # 旋鈕名 -> 這筆樣本需要的量
```

- `needed` 直接用旋鈕名當 key:conv 層是
  `{"max_queue_len": ..., "max_out_spikes": ..., "max_steps": ...}`,
  FC 目前沒有旋鈕,是空的。
  - 原本的 `max_real_queue`、`n_out_spikes`、`min_steps_needed` 三個欄位收進 `needed`。
  - 「旋鈕的需求量在哪個欄位」不用另外寫對照,現在散在 7 處以上的成對寫死程式碼都改成
    迭代 `needed`。
- 跨 batch 合併(第 19 條)照分組決定,寫在 `capacity.py` 的 `reduce_over_batch`:
  - `needed` 全部取最大:只要一筆樣本裝不下,這個 batch 就裝不下。
  - 其他(統計值)取平均。
  - 取代訓練腳本裡手寫的 mean/max,以及階段 1 的 `max_over_batch`。
    評估只看 `needed`,`spike_count` 從取最大改成取平均不影響它。

### 容量型別

```python
@dataclass(frozen=True)
class Capacity:            # 旋鈕名 -> 值,不可變、可雜湊
    values: tuple[tuple[str, int], ...]
    def __getitem__(knob) -> int
    def knobs() -> tuple[str, ...]
    def replace(**knob_values) -> Capacity
    def fits(diag) -> bool | jax.Array      # 每個旋鈕 diag.needed[旋鈕] <= 值;jit 裡回傳陣列
```

- 層提供 `capacity` 屬性跟 `with_capacity(capacity)` 方法。
  - `ConvLayer`:三個旋鈕都有。
  - `FCLayer`:`capacity` 回傳 `None`。第 2 條(階段 7)再加輸出容量跟 `max_steps`。
- 11 處 `isinstance(layer, ConvLayer)` 改成 `layer.capacity is not None`。
- `metrics.csv` 的欄位名稱不變(`conv1_max_event_queue` 這些),舊 run 的 csv 還能用同一套
  notebook 讀;旋鈕名 → csv 欄名的對照只在 `metrics_log.py` 寫一份。

### 放大縮小公式

```python
@dataclass(frozen=True)
class GrowthPolicy:        # 一層一份
    grow_factor: dict[str, float]         # 每個旋鈕
    shrink_threshold: dict[str, float]    # 會縮的旋鈕(max_out_spikes、max_steps)
    def grown(capacity, diag) -> Capacity
    def shrunk(capacity, observed: dict[str, int]) -> Capacity
```

- 公式照搬現在的 `grown_to_fit`、`shrink_max_steps`、`shrink_max_out_spikes`,
  包括「佇列長度放大時 `max_steps` 直接設成新的佇列長度」這條連動規則。
- 層不再有 `grown_to_fit`、`shrink_*` 方法,也不再有五個倍率、門檻欄位。
- yaml 的倍率、門檻還是寫在 layer entry 裡,`build_network` 拆出來組 `GrowthPolicy`。
- 「什麼時候放大、退 checkpoint、印訊息」留在 `example`。
  這一步只把訓練腳本裡呼叫層方法的地方換成呼叫 `GrowthPolicy`,拆檔留到階段 6。

### 換 `chunk_size`(第 22 條)

- 背景:掃描一步最多處理 `chunk_size` 筆事件,`max_steps` 是總共跑幾步,訓練時會照需求縮小。
  例:92.75% 那次的 conv2 結束時 `chunk_size`=4、`max_steps`=540、佇列長度 1083。
  replay 把 `chunk_size` 改成 1 時,540 步只處理得了 540 筆,佇列後面最多 543 筆會被
  靜默丟掉。
- 所以換 `chunk_size` 時 `max_steps` 要跟著改。退回佇列長度一定夠:每一步至少處理 1 筆。
- 層加 `with_chunk_size(n)`,自己把 `max_steps` 設成 `max_queue_len`。
  FC 的步數每次從輸入長度現算,只換 `chunk_size`。
- `example` 的 `force_chunk_size_one` 改用它,不再分 conv/FC。

## 5.2 執行模式(第 4 條、第 3 條其餘)

### 佇列建構拆兩段

| 段 | 內容 | conv | FC |
|---|---|---|---|
| 結構 | 只看事件,不看權重 | 每顆空間神經元的局部→全域事件、真 tap 數、Δt、每欄的 kernel 位置 (c, ky, kx) | Δt、來源神經元 |
| 數值(浮點) | a = (1 - 1/tau) ** Δt,b = 權重 × 事件增益 | 用 kernel 位置從 `w` 取值 | `w[:, 來源]` |
| 數值(整數) | 查衰減表,取整數權重碼 | 用 kernel 位置從 `q` 取值 | `q[:, 來源]` |

- 浮點數值段的運算跟現在一模一樣,只是換地方算。
  現在每個輸出 channel 各算一次 a,改成算一次再廣播,值相同。
- 整數路徑不再經過 float32(第 3c 條)。

### backend 跟單一 forward

```python
layer.forward(params, in_stream, *, backend=FLOAT, trace=False) -> LayerOutput

class LayerOutput(NamedTuple):
    stream: EventStream        # 給下一層
    result: LayerResult        # 浮點是 LayerForwardResult;量化是 QuantLayerResult
    diag: LayerDiag            # 兩種 backend 同一個型別
    trace: LayerTrace | None   # trace=True 才有
```

- backend 是 frozen dataclass,可以當 jit 的閉包:
  - `FloatBackend()`:`params` 是浮點權重,掃描用 surrogate。
  - `QuantBackend(round_mode)`:`params` 是 `QuantizedLayerParams`,逐事件整數掃描。
    另外提供 `readout(result, last_params)`,把整數 `v_final` 換回物理尺度給解碼器用。
- 四個 forward 收成一個。回傳一律是 `LayerOutput`。
- 量化版也回傳 `LayerDiag`:
  - `spike_count`、`firing_rate`、`needed` 的 `max_queue_len`、`max_out_spikes` 照常算。
  - `needed["max_steps"]` 固定 0,因為量化掃描不用 `max_steps`。
  - `LayerDiagInt` 刪掉。「有沒有出界」改由 `capacity.fits(diag)` 判斷。
- 軌跡兩種 backend 同一個型別:`spike_mask`、`v_steps`、`event_ms`。
  量化版也補上 `event_ms`(第 t 步就是佇列第 t 欄)。

### 網路層級

```python
run_network(layers, weights, input_stream, *, backend=FLOAT, trace=False) -> NetworkOutput

class NetworkOutput(NamedTuple):
    results: tuple        # 每層一個
    diags: tuple          # 每層一個
    traces: tuple | None  # trace=True 才有,已經 stop_gradient
    @property last -> 最後一層的 result
```

- 取代四支 `run_network*`。
- 每層的 `result` 都回傳。jit 裡沒用到的會被編譯器消掉,不多花時間。
  dormant 要的逐神經元活動量直接從 `results` 算,不需要另外的記錄選項。

### 整數程式收進 `salt_core/quant/`

| 新位置 | 來源 |
|---|---|
| `quant/fixed_point.py` | `fixed_point.py` 整份 |
| `quant/codes.py` | `quantize.py` 的離線常數:權重碼、衰減表、整數門檻、$i_V$ 公式 |
| `quant/ptq.py` | `quantize.py` 的 PTQ:`fake_quantize_tensor`、`quantize_params`、`quantization_error` |
| `quant/scan.py` | `core.process_event_int`、`chunk_scan` 的整數掃描 |
| `quant/backend.py` | `QuantBackend`、`QuantizedLayerParams` |

- 名字照階段 4 第 14 項的規則:`process_event_int` → `process_event`,
  `run_layer_forward_int` → `run_layer`,`LayerForwardResultInt` → `QuantLayerResult`。
  值本身是整數碼的(`build_decay_table_int`、`v_th_to_int`)不改。

### dormant(第 4 條職責對調)

- `salt_core/dormant.py` 只留 `dormant_score`。
- `dormant_report`(挑層、跑探測批、出界重算)搬到 `example`,改用 `run_network`。

### 量化評估批次化(第 3d 條)

- `QuantBackend` 可以 jit、vmap。
- jit 裡沒辦法做 Δt 的入口檢查。檢查改到原始事件進來的時候(5.3 的 `RawEvents`),
  在 host 端檢查時間是整數毫秒、在 [0, 2^31) 裡。佇列建構保證 pad 位置的 Δt 是 0,
  所以只要輸入合法,中間不會出現不合法的 Δt。
- `membrane_quantization.ipynb`、`golden_output.py` 改用批次版。

## 5.3 網路容器(第 17、6 條;第 18 條的檢查搬進來)

```python
class RawEvents(NamedTuple):       # 可以直接 jit、vmap
    event_times; x; y; c; n_real_events
    @staticmethod
    def checked(...) -> RawEvents   # host 端檢查時間(見 5.2)

@dataclass(frozen=True)
class Network:
    input_shape: tuple[int, int, int]   # 原始事件的網格 (C, H, W)
    layers: tuple
    # 建構時檢查:input_shape 接得上第一層,相鄰層接得上(check_layer_connections)
    def init(key) -> tuple
    def input_stream(raw: RawEvents) -> EventStream
    def apply(weights, raw, *, backend=FLOAT, trace=False) -> NetworkOutput
    def apply_batched(weights, raw_batch, *, backend=FLOAT, trace=False) -> NetworkOutput
    def replace_layers(layers) -> Network
```

- 網路自帶 `input_shape`,呼叫端不用再拿第一層的 `h_in`、`w_in`。
  第一層是 FC 時也能用(第 2d 條的前置條件)。
- `example/models/conv_net.py` 刪掉 `ConvNetCompressed`,只留 `build_network`(改成回傳
  `Network` 跟每層的 `GrowthPolicy`)跟 `build_decoder`。
- `data/` 不依賴 `salt_core`,所以 split → `RawEvents` 的轉換寫在 `example`。

## 決定(2026-09-27)

| 決定 | 結果 |
|---|---|
| 容量放大縮小公式放哪 | `salt_core/capacity.py` 的 `GrowthPolicy`;「什麼時候呼叫、退 checkpoint、印訊息」留在 `example` |
| 舊實驗資料怎麼讀 | 一次性轉換腳本替 `experiments/` 底下每個舊 run 補新格式的網路描述,舊檔案不動;讀取程式只認新格式 |
| 既有檔案改名 | 這個階段不改,留到階段 8 |
| `L` 改名 | `max_queue_len` |
| 診斷結構 | `LayerDiag` 分組,需求量收進 `needed`,不用對照表 |

理由:

- 公式放 `salt_core`:評估出界重算、dormant、黃金輸出腳本、訓練都要用同一套公式;
  類比 PyTorch 的 `lr_scheduler`,公式在框架裡,什麼時候 `step()` 由使用者決定。
- 一次性轉換:永久保留舊格式讀取,等於 `rebuild_layers` 的拼湊邏輯繼續留著。
- 改名留到階段 8:這個階段的 diff 只放 API 的變化。
