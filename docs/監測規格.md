# SNN 訓練監測規格

訓練 / debug SNN 要記哪些資料,以及每個量現在拿不拿得到。
定位:ReDo(訓練中回收休眠神經元)的前置,也是 max_queue_len 收縮判斷的訊號來源。

**狀態:第 1–6 節已實作(§5:`LayerDiag` 維持現狀不動;§6:`run_network(..., trace=True)` / `LayerForwardTrace` / `dormant` 搬入 `salt_core`)。第 7 節呼叫端 2026-09-13 整個改版:`example/trace_probe.py`(週期性探測 + `summary.npz`/`full_epoch_XXX.npz`)、`example/inspect_traces.py`、`example/notebooks/plot_channel_grid.ipynb` 已移除,改成訓練時(`example/training/loop.py`)逐 epoch 存純權重快照 + `example/replay_epoch.py` 事後強制 `chunk_size=1` 重跑,理由跟細節見 §7。`metrics.csv` 加欄未做,`eval_test` 的 `--trace` 已決定不做(見 §7.3)。**

## 1. 時間軸怎麼定義

這個架構沒有固定時間格,不存在「第 t 個 tick」這種東西。
內部唯一的軸是**逐 chunk 的掃描步**:每一步從某顆神經元的事件佇列取最多 `chunk_size` 筆事件、遇到第一個 spike 就提前收、指標往前推,直到整條佇列消化完或到達步數上限。
conv 和 fc 現在 `chunk_size` 都是 1,所以「一步 = 消化一筆事件」。
佇列消化完、還沒到步數上限時是空轉步,不算任何真實事件。

**真實時刻只能靠事件自己的時間標記回推**,沒有別的來源。
全域事件列表本身依時間遞增排序,所以「佇列第幾欄」對應到「輸入 `event_times` 的第幾筆」就是真實毫秒。

這條步軸對兩種 layer 意義不同:

| | conv(壓縮佇列) | fc(密集佇列) |
|---|---|---|
| 每顆神經元的佇列 | 各自獨立,只含落進自己感受野的事件 | 全體共用同一條全域事件軸 |
| 「神經元 i 第 k 步」 | i 自己收到的第 k 筆事件,不同神經元的第 k 步是不同真實時刻 | 第 k 筆全域事件,所有神經元同一時刻 |
| 步數上限 | `max_queue_len`(壓縮佇列長度) | `ceil(輸入流長度 / chunk_size)` |
| 每顆神經元的真實事件數 | 逐神經元一個數(`n_real_events` 陣列) | 全層一個純量 |

`chunk_size = 1` 時「第 k 步 ↔ 佇列第 k 欄」直接對應,不需要另外記指標。
`chunk_size > 1` 時 spike 提前收會讓指標推進不均勻,那時才需要逐步記「這步結束時消化到第幾欄」。

## 2. 三個核心量

`n` = 該層神經元數(conv:`OC × H_out × W_out`;fc:`n_out`),`max_steps` = 步數上限。

### 2.1 每神經元每步是否 spike(+可微強度)

**狀態:現成。**
`LayerForwardResult` 已有,每步都吐。

| 量 | 形狀 | 意義 |
|---|---|---|
| 是否 spike | `(n, max_steps)` bool | 該步這顆神經元有沒有真的輸出一個 spike |
| spike 落點 | `(n, max_steps)` int | spike 落在來源佇列第幾欄(conv = 局部欄,要查 `local_to_global_j`;fc = 全域事件 index) |
| `s_spike` | `(n, max_steps)` float | 只有 spike 步有意義:那個 spike 的可微分強度,forward 精確為 1;用途是接到下一層當增益 |
| `s_value` | `(n, max_steps)` float | 每步都有意義:`chunk_size=1` 時 = 該步那筆事件過 atan 之後的值 = 「離門檻多近」的連續量(跨 0.5 就 fire),本質是 `v − v_th` 的 squash |

數學上「哪個事件要不要 spike」跟 `chunk_size` 無關 —— `chunk_size` 只是一次算幾筆、spike 後跳過同視窗剩下的運算。浮點數值不是逐位元相同:不同 `chunk_size` 的加總順序不同,差在 float32 捨入範圍。實測(2026-09-27)FC 輸出層吃約 2.2 萬筆事件,跟 float64 逐事件遞迴比的最大相對誤差:`chunk_size`=1 是 6.0e-6、8 是 2.1e-6、64 是 2.3e-7、512 是 4.0e-7。

`s_value` 陣列本身不砍:它是 `LayerForwardResult` 對 decoder 的公開契約(`salt_core` 是 library,自訂時間型 decoder —— TTFS / rank-order / spike-train kernel loss —— 要在訓練路徑上讀它),每 forward 都在,`run_network` 每層都回傳,decoder 讀最後一層那份。
下面講的「留 / 不留」只是 **monitor 自己的輸出**要不要另外帶,跟 decoder 契約無關。

monitor 取哪些:
- **留**「是否 spike」+「spike 落點」(落點是還原真實時刻用的)。
- **不留** `s_spike`:「哪一步 fire」是否 spike 的 bool 已經講完,強度恆 ≈ 1 沒資訊。
- `s_value`:`LayerForwardResult` 一直帶完整 `(n, max_steps)`(decoder 契約,訓練熱路徑不變);`LayerDiag` 不另外帶(見 §5)。**`LayerForwardTrace`(§6)2026-09-13 起不再轉抄這欄**——這個架構下 `s_value` forward 數值恆等於「是否 spike」(一個 chunk 最多一筆事件跨過門檻),而 `LayerForwardTrace` 本身又是 `stop_gradient` 後才回傳,連它在 decoder 契約裡才有意義的「可微分」也用不上,留著是純重複資訊,不是分開兩份給不同消費者。

梯度:
- 有梯度的只有「超過門檻多少」,即 `s` 對 `v − v_th`、進而對權重。
- 「哪一步是 spike」這個離散選擇被 `stop_gradient` 標成常數,沒有梯度。

conv / fc 差異:
- conv 隱藏層會 fire,這個量有意義。
- fc 目前只當輸出層,`v_th = 10^9` 永不 fire,是否 spike 恆為 False;要監測 spike 得是會 fire 的層。

### 2.2 每神經元每步的膜電位

**狀態:已實作(`LayerForwardTrace.v_steps`,見 §6)。**
每步結束的膜電位(套過 soft reset)在掃描迴圈內每步都算了,但正常 `run_layer_forward` 只回「最後一步」的 `(n,)`(`v_final`);`run_layer_forward_traced` 把每步都疊出來 → `(n, max_steps)` 軌跡,最後一欄 = `v_final`。

| 量 | 形狀 | 現狀 |
|---|---|---|
| 最終膜電位 | `(n,)` | `LayerForwardResult.v_final` |
| 逐步膜電位軌跡(reset 後) | `(n, max_steps)` | `LayerForwardTrace.v_steps`(traced 路徑) |
| 不 reset 的逐事件電壓 | `(n, max_steps, chunk_size)` | **不留** |

「哪裡 spike」直接看 2.1 的「是否 spike」bool,不必靠沒 reset 的軌跡。
沒 reset 的軌跡唯一多給的是「spike 那一點衝過門檻多少」(reset 後那格被壓到 ≈ 0,看不到過衝量);過衝量是飽和 / dead-gradient 訊號,要就另開 surrogate 斜率 opt-in,不在預設。

梯度:膜電位由仿射映射的 associative scan + soft reset 組成,全 JAX 原生可微,對權重天生有梯度。
但 monitor 定位是診斷,規劃是 `stop_gradient` 後才回傳,不進 loss。

conv / fc 差異:同一套機制,只差步軸意義(見第 1 節表)。

### 2.3 每神經元每步的事件

**狀態:分兩塊。**

「每步消化幾筆事件」:
- `chunk_size = 1` 時恆為 1(空轉步為 0),沒有資訊量。
- `chunk_size > 1` 才有意義(逐步的有效事件數),目前沒吐,短期不需要。

「每顆神經元收到幾筆真實事件、分別在什麼時刻」:
- 總數現成:conv 是佇列建構端的 `n_real_events` 逐神經元陣列,fc 是全層純量。
- 逐步對到真實毫秒:`chunk_size = 1` 下用第 3 節的公式即可,只需要把 conv 的 `local_to_global_j` 帶出 forward、加上每層自己的輸入 `event_times`。

conv / fc 差異:
- conv:每顆神經元本來就有自己的事件子序列,形狀天生對;需要 `local_to_global_j` 把局部欄查回全域事件。
- fc:每步就是第 k 筆全域事件,直接是全域 index,不需查表。

## 3. 還原到真實毫秒

把「神經元 i 第 k 步」還原成「實際發生在毫秒 t」。
**已實作**:`run_layer_forward_traced` 吐逐步 `pointer` 裸陣列(每步消化前佇列到第幾欄),`salt_core/trace.py` 的 `resolve_ms_*` 純函式把它轉成 `LayerForwardTrace.event_ms` `(n, max_steps)`,空轉步 = `nan`。`ConvLayer` / `FCLayer` 的 `forward` 在 `trace=True` 時內部呼叫,呼叫端不必自己組。

| layer | 算法 | 用到 |
|---|---|---|
| conv | `t = event_times[local_to_global_j[i, pointer[i,k]]]`;`pointer ≥ n_real_events[i]` → `nan` | `ConvQueueStructure.local_to_global_j`(用 `tile_channels` 展開到每個 channel)+ 該層輸入 `event_times` |
| fc | `t = event_times[pointer[i,k]]`;`pointer ≥ n_real_events` → `nan`(`pointer` 密集版直接是全域 index) | 該層輸入 `event_times` |

`chunk_size = 1` 時 `pointer[i,k] = k`,`event_ms` 精確對到一筆事件。
`chunk_size > 1` 時 `event_ms` 是「這步從哪個時刻開始」(視窗首事件);逐事件展開沒做(見 §6.3 / TODO)。

## 4. 職責切分

### 4.1 三個 package 的分工

- **core 只吐生資料**,不 reduce、不預判分析;逐神經元逐步的陣列原樣送出計算圖,`stop_gradient` 後回傳。
- **`salt_core` 放通用 helper**:`dormant_score`(`|h_i| / 層內 |h| 均值`)在 `salt_core/dormant.py` —— 活動分布是 SNN 通用除錯量,不是 example 專屬。挑層、跑探測批的 `dormant_report` 是應用的決定,在 `example/dormant.py`。(步 → 真實毫秒不走 helper,見第 3 節。)
- **`example` 只留**:寫 `metrics.csv` / 圖、選探測批次、逐層梯度範數(在 forward 外算)。

### 4.2 LayerDiag 與 LayerForwardTrace 的分工線

**只有一條線:誰讀它。**

- 訓練中有機制會自動讀 → `LayerDiag`,永遠開。
- 只有人 / 離線分析讀 → `LayerForwardTrace`,`run_network(..., trace=True)` 才收。

`LayerDiag` **沒有 shape 上限**。
消費者決定 bucket 這條規則優先:某個訓練機制真的需要每步一個 `(n, max_steps)` 陣列,它還是進 `LayerDiag`。
只是 `LayerDiag` 在永遠編譯的熱 forward 裡,裡面的東西越貴每個 batch 都在付 —— 這是成本考量,不是分工線。

**「會讀」指現役消費者,不是「以後某機制大概會用」。**
為還沒實作的機制(例如 ReDo)先把量塞進 `LayerDiag`,就是違反這條線 —— 那些量等機制真的落地、資料來源定案(§7)再放。

## 5. LayerDiag(永遠開)

**維持現有 4 欄,不加東西。**

| 欄 | 現役消費者 |
|---|---|
| `spike_count` / `firing_rate` | `metrics.csv` logging(哨兵指標) |
| `needed`(旋鈕名 → 這筆樣本需要的容量) | `GrowthPolicy.grown`(出界 → 放大)、`metrics.csv` 的用量欄位 |

`run_network` 每層都收 `LayerDiag` 跟結果(`NetworkOutput.diags` / `results`),這條管道現成。

討論過程中曾列出要往 `LayerDiag` 加的東西 —— `v_final` 的 mean/std/min/max、`nonfinite` flag、事件放大比、ReDo 的逐神經元 `(n,)` 摘要(spike 數 / `Σ_t s_value` / `v_final` / 真實佇列長度)—— **依 §4.2 全部不加**:

- **ReDo 沒實作。** `dormant_report` 是每 epoch 自己跑一次 probe forward 收逐神經元活動,不靠每-batch 的 `LayerDiag`。這些量現在沒有每-batch 消費者。
- ReDo 真的要做時,它的逐神經元活動來源(每 epoch probe forward / 訓練批滑動平均 / traced 路徑)在 §7 一起定,不預先塞。
- `v_final` 統計、`nonfinite`、事件放大比是 logging / 診斷量:`example` 的 logger 從手上已有的 `LayerForwardResult` / `EventStream` 現場算,或走 §6 的 traced 路徑,不常駐。

`dormant` 從 `example/` 搬進 `salt_core`(TODO 要的)**不需要動 `LayerDiag`**:`dormant_report` 從 `Network.apply_batched` 回傳的每層結果算逐神經元活動(`example/dormant.py`),`dormant_score` 拆成可重用的純歸約 primitive。已完成。

## 6. LayerForwardTrace / run_network(trace=True)(逐步軌跡,已實作)

角色:人工 debug 自訂 decoder / 動力學 + 週期性深度監測。
是 `run_network` 的 `trace` 參數(2026-09-27 架構審查階段 5.2b 起;之前是另一支函式
`run_network_traced`,跟浮點 / 整數兩種 backend 組合出四支函式,收成一支)。

### 6.1 回傳

| 呼叫 | `NetworkOutput` 的內容 | 用途 |
|---|---|---|
| `run_network(...)` | `results`、`diags` 每層一份,`traces` 是 `None` | 訓練熱路徑 |
| `run_network(..., trace=True)` | 另外 `traces` 每層一份 `LayerForwardTrace`,`stop_gradient` 後 | forward-only 週期性 probe、事後重跑 |

浮點、整數 backend 都用同一個 `LayerForwardTrace`;整數 backend 的 `v_steps` 是暫存器整數值,
第 t 步就是佇列第 t 欄。

`LayerForwardTrace` 逐層一份,全部 `(n, max_steps)`:

| 欄 | 意義 |
|---|---|
| `spike_mask` | 轉抄 `LayerForwardResult`,讓一份 monitor 自成完整 dump |
| `v_steps` | 每步 chunk 結束(reset 後)的膜電位 = 完整膜電位軌跡;最後一欄 = `v_final` |
| `event_ms` | 每步消化的(首)事件真實毫秒;空轉步 = `nan`。conv 走 `local_to_global_j` 查表,fc 的 `pointer` 直接是全域 index |

**`s_value` 2026-09-13 起不轉抄進來**(原本這裡):這個架構下它的 forward 數值
恆等於 `spike_mask`(§2.1 已證明:一個 chunk 裡最多一筆事件跨過門檻),而
`LayerForwardTrace` 整包又是 `stop_gradient` 後才回傳——原本設想的「自訂時間
型 decoder 作者要 debug 的原始可微輸出」這個理由,在這條 forward-only 的路
上本來就不成立(可微分那份活在 `LayerForwardResult.s_value`,訓練熱路徑,
不受影響)。留著純粹是跟 `spike_mask` 重複的資訊。

### 6.2 實作

- `salt_core/float/scan.py` 的 `run_layer_forward_traced` 跟 `run_layer_forward` 共用同一個 scan 內核(`_run_layer_scan`,`trace` 是 Python 端靜態 bool),`LayerForwardResult` 五欄相同,只多疊 `(v_steps, pointer)` 兩條 per-step 裸陣列輸出。
- `ConvLayer` / `FCLayer` 只有一個 `forward`,`trace=True` 時 `LayerOutput.trace` 帶軌跡,其他欄位不變。
- 步 → 毫秒的還原在 `salt_core/trace.py`(`resolve_ms_conv` / `resolve_ms_fc`,純函式)。
- **不進 `train_step`**:`trace` 是 Python 端靜態 bool,`trace=True` 是另一個編譯目標,訓練熱路徑編譯不受影響。
- **max_queue_len 收縮不需要這條路**:它的訊號 `needed["max_queue_len"]` 在 `LayerDiag` 每 batch 已經有。

### 6.3 `chunk_size > 1` 的 `event_ms`

`pointer` 是「這步消化前佇列到第幾欄」。
`chunk_size = 1` 時每步剛好對一筆事件,`event_ms` 精確。
`chunk_size > 1` 時 `event_ms` 是「這步從哪個時刻開始」(視窗首事件),不是視窗內每筆;要逐事件得看 `chunk_size` 展開,現階段沒做(見 §2.3 / TODO)。

## 7. 呼叫端(`example`)

**2026-09-13 決定,整段改版**:原本 `example/trace_probe.py` 週期性對固定探測批
跑 `run_network_traced`、dump `summary.npz`/`full_epoch_XXX.npz`,`example/
inspect_traces.py` 讀回印報表,`example/notebooks/plot_channel_grid.ipynb`
畫 `summary.npz` 的空間熱圖——三者都已移除。原因:

- `summary.npz` 4 欄裡,`s_value_sum` 數學上恆等於 `spike_count`(`salt_core/float/scan.py`
  的 `n_valid_in_chunk` 邏輯保證一個 chunk 最多一個 1,兩者是同一組 0/1 加總,
  逐位元證明過、不是猜的),是純重複欄位。
- `full_epoch_XXX.npz` 存的 `v_steps`/`event_ms` 在 `chunk_size > 1` 的層上,
  只留得住「一個 scan 步吃掉的最多 `chunk_size` 筆真實事件裡,第一筆的時間」
  跟「全部合成完的結果」,中間那幾筆各自的時間/貢獻在合成當下已經不可逆
  遺失,事後無法從結果反推(這不是「精度不夠」,是資訊在計算當下就已經
  被摧毀)。
- forward 的結果數學上跟 `chunk_size` 無關,數值只差 float32 捨入(見 §2.1 表格下的實測)——所以
  與其為了保留逐事件粒度另外設計新的存檔格式,不如利用「權重 + 原始樣本唯一決定整條軌跡」這件事:
  只要某個 epoch 的權重還留著,事後把 `chunk_size` 覆蓋成 1 重跑,就能拿到每一步對應一筆事件的
  結果,跟訓練當下(不管原本用哪個 `chunk_size`)只差 float32 捨入。

### 7.1 訓練側:逐 epoch 權重快照(`example/training/loop.py`,已實作)

不再另開一支 `TraceProbe` 類別。`run_epochs` 每個成功 epoch 的
`checkpointer.save` 之後,`train.weight_snapshot_every > 0` 且
`epoch % weight_snapshot_every == 0` 時,用 `salt_core.io.save_weights` 存一份
權重,連同這個 epoch 實際用的網路(含容量,縮小之前的值;跟 `params.npz`/`best_params.npz`
同格式,不含 optimizer state)到 `experiments/<run>/weights/epoch_XXX.npz`(路徑命名見
`example/utils.py` 的 `weight_snapshot_path`)。

- 只存權重跟網路描述(58KB/epoch 量級,`checkpoint.npz` 含 optimizer state 要 174KB),
  跟「每個 epoch 覆寫一份、只為續練用」的 `checkpoint.npz` 是兩回事——這裡
  逐 epoch 各自保留,才能事後回頭看任何一個存過的 epoch。
- config 旋鈕(`train:` 區塊):`weight_snapshot_every`(0 = 關)。
- 出界重練退回某個 epoch 重編譯續跑時,沿用同一個快照目錄,已存的快照
  不會被清掉(重跑到同一個 epoch 號會覆寫該檔,語意跟 `checkpoint.npz` 出界
  退回一致)。

### 7.2 讀端:`example/replay_epoch.py`(已實作)

吃 `<exp_dir>` + `epoch` 號:

1. 讀 `weights/epoch_XXX.npz`(`salt_core.io.load_weights`),拿到那個 epoch 的權重跟
   當下的網路(含容量)。
2. 每一層 `with_chunk_size(1)`:`ConvLayer` 同時把 `max_extra_steps` 設成一定夠的值
   (總步數 = `max_queue_len`,避免沿用舊 `chunk_size` 校準出的值太小、silently 截斷
   掃描;chunk_size=1 時這個值是 0);`FCLayer` 的 `max_extra_steps` 不用改(chunk_size=1 時
   需求一定是 0,基本步數 = 輸入流長度,從輸入流現算)。
3. 重建同一筆原始樣本(跟
   訓練時同一個 `seed_train`/`train_size` 切出的 train split,取指定
   `--sample`),餵進 `run_network(..., trace=True)`。

回傳每層的 `LayerForwardTrace`,`v_steps`/`event_ms` 現在保證每一步對應
**剛好一筆**真實事件,不再有 `chunk_size > 1` 那種「一步吃好幾筆」的模糊
地帶。CLI 用法印每層的 `summarize_trace_scalars`(`salt_core/trace.py`,
沿用既有函式,沒重刻)。

**權重快照的覆蓋範圍是唯一限制**:某個 epoch 沒被 `weight_snapshot_every`
命中,那個 epoch 的權重就已經不在了(`checkpoint.npz` 每個 epoch 覆寫,只剩
最新一份),沒有東西可以重跑——這是用「存權重、事後算」換掉「存逐步資料」
必然的取捨,想看哪個 epoch 要事先讓 `weight_snapshot_every` 命中它。

### 7.3 還沒定的

1. **`eval_test` 的 `--trace`:2026-09-11 決定不做。** 原本設想「這裡沒有跨
   epoch 可比、擾動訓練的顧慮,政策問題大半消失」只是講「做起來比較沒包袱」,
   不是「這件事跟跑分數是同一個任務」——`eval_test.py` 的定位就是跑分數
   (accuracy / loss / confusion matrix,已實作,跟這份監測規格是不同關注點,
   不在這裡追蹤),深入分析(某神經元為什麼這樣、畫圖之類)是另一種消費者,
   硬塞進同一支腳本違反「一支檔案只做一件事」。**深入分析工具已經做出來
   了,是 `example/replay_epoch.py`**(見 §7.2)。`eval_test.py` 的
   `_load_run_record`/`_rebuild_layers`/`_load_params` 當初就已經搬進
   `example/utils.py` 共用(`load_run_record`/`rebuild_layers`/
   `load_run_params`),`replay_epoch.py` 直接重用,不是新的第二個消費者
   才要搬——這件事已經解決。
2. **dormant / ReDo 的逐神經元活動來源:2026-09-11 決定 ReDo 本身先擱置,這裡跟著擱置。**
   討論過程查證:(a) ReDo 是 Sokar et al. 2023 針對 ANN/RL non-stationary target 驗證的方法,
   查無 SNN 場景下「偵測快死神經元、重置權重復活」這個具體流程被驗證過的文獻;(b) 我們的
   conv 權重是整個 output channel 共用一顆 kernel,但活動量是逐 `(channel, 空間位置)` 算,
   兩者粒度不一致,要重置得先決定聚合規則;(c) conv1 直接接原始事件,零放電有兩種不同成因
   ——輸入端根本沒事件掉進來(資料幾何造成,重置無效)vs 輸入有到但權重跨不過門檻(才是
   initialization 造成、reset 有意義的情況)——現在沒有辦法分辨這兩種。(d) 沒有證據顯示現有
   `init_k=5.0` baseline 因為沒有 ReDo 出問題,見 [`TODO.md`](TODO.md)「開放題」:V6 驗證過
   `init_k=√3` 70% 休眠仍訓到 0.795,`init_k=5` 休眠會自己降。真的要疊深網路(尤其 FC→FC)
   再重新評估這整個方向,不是現在就得決定活動來源要怎麼接。
3. **`metrics.csv` 加欄**:從 traces 現場算的純量(dead-step 比例 / 飽和 / `nonfinite`)。
   原本等 ReDo 準則定案再做決定,ReDo 已擱置(見上),這裡一併擱置,避免加沒有消費者的欄
   (§4.2)。

### 7.4 實驗目錄的輸出檔

一次訓練 run 寫在 `experiments/<run>/` 底下。

**`train/metrics.csv`**:一個 epoch 一列,是唯一能直接畫「隨 epoch 變化」折線圖的來源。

| 欄位 | 幾份 | 意思 |
|---|---|---|
| `epoch`、`train_loss`、`val_accuracy` | 一份 | |
| `val_capacity_regrows` | 一份 | val 評估時容量出界、放大重算的次數 |
| `<層>_max_event_queue`、`<層>_max_layer_spikes`、`<層>_max_extra_steps` | 每個有容量的層(FC 沒有 `max_event_queue`) | 這個 epoch 結束時的容量(`max_queue_len`、`max_out_spikes`、`max_extra_steps`) |
| `<層>_obs_event_queue`、`<層>_obs_layer_spikes`、`<層>_obs_extra_steps` | 同上 | 這個 epoch 實際用到的最大值,跟上一列對照 |
| `<層>_firing_rate`、`<層>_grad_norm` | 每一層 | batch 平均 |
| `<層>_dormant_frac` | `train.dormant_layers` 列的每一層(沒填就沒有這欄) | 沒算的 epoch 填 nan |
| `dormant_capacity_regrows` | 一份 | dormant 統計時容量出界、放大重算的次數 |
| `decoder_<名稱>` | 依解碼器 | 解碼器自己的指標 |

**`train/run.yaml`**:一次 run 的紀錄,不是數列,適合當圖表標題或圖例。
開訓時先寫前五個欄位,訓練結束時整份覆寫。
欄位:`config`(完整 config 快照)、`git_commit`、`xla_flags`、`timestamp`、
`resumes`(跨行程續練的紀錄,每次一筆:`from_epoch`、當時的 `git_commit`、`timestamp`;
沒續練過是空的)、`best`(`epoch`、`val_accuracy`)、`network`(結束時的網路描述,`salt_core.io.network_to_dict`
的格式,含每層容量)、`last_epoch_obs`(最後一個 epoch 每個
有容量的層各旋鈕的最大需求)、`capacity_events`(訓練中容量的放大縮小,依發生順序)。

`capacity_events` 每一筆:

| 欄位 | 意思 |
|---|---|
| `kind` | `grow`(訓練 batch 出界、放大後重來)或 `shrink`(epoch 跑完後縮小) |
| `epoch` | 發生在哪個 epoch |
| `batch` | 只有 `grow`:出界的 batch |
| `resumed_from_epoch` | 只有 `grow`:退回哪個 epoch 的 checkpoint;`null` 是從頭重來 |
| `changes` | 每個變了的旋鈕一筆:`layer`、`knob`、`old`、`new`、`observed`(觸發的需求量;`shrink` 是這個 epoch 的最大需求) |

**`train/` 的權重**(都帶存檔當下的網路描述):`params.npz`(最後一個 epoch)、
`best_params.npz`(val 最好的 epoch)、`checkpoint.npz`(續練用,每個 epoch 覆寫)。
逐 epoch 快照在 `weights/epoch_XXX.npz`,見 §7.1。

`checkpoint.npz` 存接著練需要的全部狀態:下一個 epoch 要用的網路(縮小之後)、權重、
optimizer state、shuffle key、最後完成的 epoch、best(權重、網路、`val_accuracy`、epoch)、
紀錄(已完成 epoch 的 metrics 列、容量事件)。先寫暫存檔再換名。
行程當掉後用 `python -m example.train --resume experiments/<run>` 接著練,
config 用 `run.yaml` 裡開訓時的快照;已經跑完的 run(有 `params.npz`)不能續練。

**`eval/`**:`example/eval_test.py` 跟 `example/plot_eval.py` 寫的跑分結果,
`<which>` 是 `test` 或 `val`。

- `<which>.yaml`:`accuracy`、`loss`、`capacity_regrows`、`confusion_matrix`,
  加上 `which`、`n_samples`、`seed`、`params`(best 或 final)、`git_commit`、
  `timestamp`。
- `<which>_preds.npz`:逐樣本的 `preds`、`labels`。
- `<which>_confusion.png`:混淆矩陣圖。
