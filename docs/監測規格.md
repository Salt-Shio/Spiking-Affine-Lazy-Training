# SNN 訓練監測規格

訓練 / debug SNN 要記哪些資料,以及每個量現在拿不拿得到。
定位:ReDo(訓練中回收休眠神經元)的前置,也是 L 收縮判斷的訊號來源。
背景見 [`TODO.md`](TODO.md)「SNN 活動 monitor」。

**狀態:第 1–6 節已實作(§5:`LayerDiag` 維持現狀不動;§6:`run_network_traced` / `LayerForwardTrace` / `dormant` 搬入 `salt_core`)。第 7 節訓練側消費端(`example/trace_probe.py`)+ 讀端(`example/inspect_traces.py`)已實作,見 §7;`metrics.csv` 加欄未做,`eval_test` 的 `--trace` 已決定不做(見 §7.3)。**

## 1. 時間軸怎麼定義

這個架構沒有固定時間格,不存在「第 t 個 tick」這種東西。
內部唯一的軸是**逐 chunk 的掃描步**:每一步從某顆神經元的事件佇列取最多 `chunk_size` 筆事件、遇到第一個 spike 就提前收、指標往前推,直到整條佇列消化完或到達步數上限。
conv 和 fc 現在 `chunk_size` 都是 1,所以「一步 = 消化一筆事件」。
佇列消化完、還沒到步數上限時是空轉步,不算任何真實事件。

**真實時刻只能靠事件自己的時間標記回推**,沒有別的來源。
全域事件列表本身依時間遞增排序,所以「佇列第幾欄」對應到「輸入 `event_times` 的第幾筆」就是真實毫秒。

這條步軸對兩種 layer 意義不同:

| | conv(壓縮佇列) | fc(密集佇列) |
|---|---|---|
| 每顆神經元的佇列 | 各自獨立,只含落進自己感受野的事件 | 全體共用同一條全域事件軸 |
| 「神經元 i 第 k 步」 | i 自己收到的第 k 筆事件,不同神經元的第 k 步是不同真實時刻 | 第 k 筆全域事件,所有神經元同一時刻 |
| 步數上限 | `L`(壓縮佇列長度) | `ceil(輸入流長度 / chunk_size)` |
| 每顆神經元的真實事件數 | 逐神經元一個數(`n_real_events` 陣列) | 全層一個純量 |

`chunk_size = 1` 時「第 k 步 ↔ 佇列第 k 欄」直接對應,不需要另外記指標。
`chunk_size > 1` 時 spike 提前收會讓指標推進不均勻,那時才需要逐步記「這步結束時消化到第幾欄」。

## 2. 三個核心量

`n` = 該層神經元數(conv:`OC × H_out × W_out`;fc:`n_out`),`max_steps` = 步數上限。

### 2.1 每神經元每步是否 spike(+可微強度)

**狀態:現成。**
`LayerForwardResult` 已有,每步都吐。

| 量 | 形狀 | 意義 |
|---|---|---|
| 是否 spike | `(n, max_steps)` bool | 該步這顆神經元有沒有真的輸出一個 spike |
| spike 落點 | `(n, max_steps)` int | spike 落在來源佇列第幾欄(conv = 局部欄,要查 `local_to_global_j`;fc = 全域事件 index) |
| `s_spike` | `(n, max_steps)` float | 只有 spike 步有意義:那個 spike 的可微分強度,forward 精確為 1;用途是接到下一層當增益 |
| `s_value` | `(n, max_steps)` float | 每步都有意義:`chunk_size=1` 時 = 該步那筆事件過 atan 之後的值 = 「離門檻多近」的連續量(跨 0.5 就 fire),本質是 `v − v_th` 的 squash |

「哪個事件要不要 spike」跟 `chunk_size` 無關 —— `chunk_size` 只是一次算幾筆、spike 後跳過同視窗剩下的運算,forward 結果逐位元不變。

`s_value` 陣列本身不砍:它是 `LayerForwardResult` 對 decoder 的公開契約(`salt_core` 是 library,自訂時間型 decoder —— TTFS / rank-order / spike-train kernel loss —— 要在訓練路徑上讀它),每 forward 都在,`run_network` 留最後一層那份給 decoder。
下面講的「留 / 不留」只是 **monitor 自己的輸出**要不要另外帶,跟 decoder 契約無關。

monitor 取哪些:
- **留**「是否 spike」+「spike 落點」(落點是還原真實時刻用的)。
- **不留** `s_spike`:「哪一步 fire」是否 spike 的 bool 已經講完,強度恆 ≈ 1 沒資訊。
- `s_value`:`LayerForwardResult` 一直帶完整 `(n, max_steps)`(decoder 契約);`LayerDiag` 不另外帶(見 §5);要逐步 `s_value` 走 `run_network_traced` 的 `LayerForwardTrace`(見 §6)。

梯度:
- 有梯度的只有「超過門檻多少」,即 `s` 對 `v − v_th`、進而對權重。
- 「哪一步是 spike」這個離散選擇被 `stop_gradient` 標成常數,沒有梯度。

conv / fc 差異:
- conv 隱藏層會 fire,這個量有意義。
- fc 目前只當輸出層,`v_th = 10^9` 永不 fire,是否 spike 恆為 False;要監測 spike 得是會 fire 的層。

### 2.2 每神經元每步的膜電位

**狀態:已實作(`LayerForwardTrace.v_steps`,見 §6)。**
每步結束的膜電位(套過 soft reset)在掃描迴圈內每步都算了,但正常 `run_layer_forward` 只回「最後一步」的 `(n,)`(`v_final`);`run_layer_forward_traced` 把每步都疊出來 → `(n, max_steps)` 軌跡,最後一欄 = `v_final`。

| 量 | 形狀 | 現狀 |
|---|---|---|
| 最終膜電位 | `(n,)` | `LayerForwardResult.v_final` |
| 逐步膜電位軌跡(reset 後) | `(n, max_steps)` | `LayerForwardTrace.v_steps`(traced 路徑) |
| 不 reset 的逐事件電壓 | `(n, max_steps, chunk_size)` | **不留** |

「哪裡 spike」直接看 2.1 的「是否 spike」bool,不必靠沒 reset 的軌跡。
沒 reset 的軌跡唯一多給的是「spike 那一點衝過門檻多少」(reset 後那格被壓到 ≈ 0,看不到過衝量);過衝量是飽和 / dead-gradient 訊號,要就另開 surrogate 斜率 opt-in,不在預設。

梯度:膜電位由仿射映射的 associative scan + soft reset 組成,全 JAX 原生可微,對權重天生有梯度。
但 monitor 定位是診斷,規劃是 `stop_gradient` 後才回傳,不進 loss。

conv / fc 差異:同一套機制,只差步軸意義(見第 1 節表)。

### 2.3 每神經元每步的事件

**狀態:分兩塊。**

「每步消化幾筆事件」:
- `chunk_size = 1` 時恆為 1(空轉步為 0),沒有資訊量。
- `chunk_size > 1` 才有意義(逐步的有效事件數),目前沒吐;conv 就算把 `chunk_size` 調大也無效(見 [`TODO.md`](TODO.md) 的設計限制),所以短期不需要。

「每顆神經元收到幾筆真實事件、分別在什麼時刻」:
- 總數現成:conv 是佇列建構端的 `n_real_events` 逐神經元陣列,fc 是全層純量。
- 逐步對到真實毫秒:`chunk_size = 1` 下用第 3 節的公式即可,只需要把 conv 的 `local_to_global_j` 帶出 forward、加上每層自己的輸入 `event_times`。

conv / fc 差異:
- conv:每顆神經元本來就有自己的事件子序列,形狀天生對;需要 `local_to_global_j` 把局部欄查回全域事件。
- fc:每步就是第 k 筆全域事件,直接是全域 index,不需查表。

## 3. 還原到真實毫秒

把「神經元 i 第 k 步」還原成「實際發生在毫秒 t」。
**已實作**:`run_layer_forward_traced` 吐逐步 `pointer` 裸陣列(每步消化前佇列到第幾欄),`salt_core/monitor.py` 的 `resolve_ms_*` 純函式把它轉成 `LayerForwardTrace.event_ms` `(n, max_steps)`,空轉步 = `nan`。`ConvLayer` / `FCLayer` 的 `forward_traced` 內部呼叫,呼叫端不必自己組。

| layer | 算法 | 用到 |
|---|---|---|
| conv | `t = event_times[local_to_global_j[i, pointer[i,k]]]`;`pointer ≥ n_real_events[i]` → `nan` | `CompressedConvQueue.local_to_global_j` + 該層輸入 `event_times` |
| fc | `t = event_times[pointer[i,k]]`;`pointer ≥ n_real_events` → `nan`(`pointer` 密集版直接是全域 index) | 該層輸入 `event_times` |

`chunk_size = 1` 時 `pointer[i,k] = k`,`event_ms` 精確對到一筆事件。
`chunk_size > 1` 時 `event_ms` 是「這步從哪個時刻開始」(視窗首事件);逐事件展開沒做(見 §6.3 / TODO)。

## 4. 職責切分

### 4.1 三個 package 的分工

- **core 只吐生資料**,不 reduce、不預判分析;逐神經元逐步的陣列原樣送出計算圖,`stop_gradient` 後回傳。
- **`salt_core` 放通用 helper**:`dormant_score`(`|h_i| / 層內 |h| 均值`)已從 `example/dormant.py` 搬進 `salt_core/dormant.py` —— 活動分布是 SNN 通用除錯量,不是 example 專屬。(步 → 真實毫秒不走 helper,見第 3 節。)
- **`example` 只留**:寫 `metrics.csv` / 圖、選探測批次、逐層梯度範數(在 forward 外算)。

### 4.2 LayerDiag 與 LayerForwardTrace 的分工線

**只有一條線:誰讀它。**

- 訓練中有機制會自動讀 → `LayerDiag`,永遠開。
- 只有人 / 離線分析讀 → `LayerForwardTrace`,走另一支函式 `run_network_traced`。

`LayerDiag` **沒有 shape 上限**。
消費者決定 bucket 這條規則優先:某個訓練機制真的需要每步一個 `(n, max_steps)` 陣列,它還是進 `LayerDiag`。
只是 `LayerDiag` 在永遠編譯的熱 forward 裡,裡面的東西越貴每個 batch 都在付 —— 這是成本考量,不是分工線。

**「會讀」指現役消費者,不是「以後某機制大概會用」。**
為還沒實作的機制(例如 ReDo)先把量塞進 `LayerDiag`,就是違反這條線 —— 那些量等機制真的落地、資料來源定案(§7)再放。

## 5. LayerDiag(永遠開)

**維持現有 4 欄,不加東西。**

| 欄 | 現役消費者 |
|---|---|
| `spike_count` / `firing_rate` | `metrics.csv` logging(哨兵指標) |
| `max_real_queue` | `ConvLayer.grown_to_fit`(L 出界 → 放大) |
| `n_out_spikes` | `ConvLayer.grown_to_fit`(輸出上界出界 → 放大) |

`run_network` 已經每層都收 `LayerDiag`(只有 `LayerForwardResult` 是最後一層),這條管道現成。

討論過程中曾列出要往 `LayerDiag` 加的東西 —— `v_final` 的 mean/std/min/max、`nonfinite` flag、事件放大比、ReDo 的逐神經元 `(n,)` 摘要(spike 數 / `Σ_t s_value` / `v_final` / 真實佇列長度)—— **依 §4.2 全部不加**:

- **ReDo 沒實作。** `dormant_report` 是每 epoch 自己跑一次 probe forward 收逐神經元活動,不靠每-batch 的 `LayerDiag`。這些量現在沒有每-batch 消費者。
- ReDo 真的要做時,它的逐神經元活動來源(每 epoch probe forward / 訓練批滑動平均 / traced 路徑)在 §7 一起定,不預先塞。
- `v_final` 統計、`nonfinite`、事件放大比是 logging / 診斷量:`example` 的 logger 從手上已有的 `LayerForwardResult` / `EventStream` 現場算,或走 §6 的 traced 路徑,不常駐。

`dormant` 從 `example/` 搬進 `salt_core`(TODO 要的)**不需要動 `LayerDiag`**:`dormant_report` 保留自己逐層收逐神經元活動的做法(`salt_core/dormant.py` 的 `_per_neuron_activity`,鏡射 `run_network`),`dormant_score` 拆成可重用的純歸約 primitive。已完成。

## 6. LayerForwardTrace / run_network_traced(逐步軌跡,已實作)

角色:人工 debug 自訂 decoder / 動力學 + 週期性深度監測。
不是 flag,是**另一支函式** `run_network_traced` —— 正常 `run_network` 一個字不動,traced 路徑平行存在。

### 6.1 兩條路

| 路 | 回傳 | 用途 |
|---|---|---|
| `run_network`(正常) | `(最後一層 LayerForwardResult, [LayerDiag])` | 訓練熱路徑 |
| `run_network_traced`(逐步軌跡) | `[LayerForwardTrace]`,`stop_gradient` 後 | forward-only 週期性 probe,dump `.npz` |

`LayerForwardTrace` 逐層一份,全部 `(n, max_steps)`:

| 欄 | 意義 |
|---|---|
| `spike_mask` / `s_value` | 轉抄 `LayerForwardResult`,讓一份 monitor 自成完整 dump |
| `v_steps` | 每步 chunk 結束(reset 後)的膜電位 = 完整膜電位軌跡;最後一欄 = `v_final` |
| `event_ms` | 每步消化的(首)事件真實毫秒;空轉步 = `nan`。conv 走 `local_to_global_j` 查表,fc 的 `pointer` 直接是全域 index |

`s_value` `(n, max_steps)` 留在這裡:自訂時間型 decoder 作者要 debug 的原始可微輸出。

### 6.2 實作

- `chunk_scan.run_layer_forward_traced` 跟 `run_layer_forward` 共用同一個 scan 內核(`_run_layer_scan`,`trace` 是 Python 端靜態 bool),`LayerForwardResult` 五欄逐位元相同,只多疊 `(v_steps, pointer)` 兩條 per-step 裸陣列輸出。
- `ConvLayer` / `FCLayer` 各有 `forward_traced`,跟 `forward` 共用私有 `_run_forward`;`forward` 的輸出契約不動。
- 步 → 毫秒的還原在 `salt_core/monitor.py`(`resolve_ms_compressed` / `resolve_ms_dense`,純函式)。
- **不進 `train_step`**:`run_network_traced` 是另一個編譯目標,訓練熱路徑編譯不受影響。
- **L 收縮不需要這條路**:它的訊號 `max_real_queue` 在 `LayerDiag` 每 batch 已經有。

### 6.3 `chunk_size > 1` 的 `event_ms`

`pointer` 是「這步消化前佇列到第幾欄」。
`chunk_size = 1` 時每步剛好對一筆事件,`event_ms` 精確。
`chunk_size > 1` 時 `event_ms` 是「這步從哪個時刻開始」(視窗首事件),不是視窗內每筆;要逐事件得看 `chunk_size` 展開,現階段沒做(見 §2.3 / TODO)。

## 7. 呼叫端(`example`)

### 7.1 訓練側:`example/trace_probe.py`(已實作)

`TraceProbe`,跟 `MetricsLog` / `Checkpointer` 同層級,`train.probe_every > 0` 才建構、
傳進 `run_epochs`,在每個成功 epoch 的 `checkpointer.save` 之後、`due(epoch)` 為真時跑。

- **探測批**:固定取 train split 前 `probe_samples` 筆(預設 8),建構時切好、之後不換,

  (不整批 vmap:FC 密集佇列記憶體隨樣本數線性長)。
- **輸出**(`experiments/<run>/traces/`):
  - `summary.npz` —— 每個探測 epoch 重寫。逐神經元 `(E, n)`:`{層名}__spike_count` /
    `__s_value_sum` / `__v_final` / `__idle_frac`,對步軸縮減、對 `probe_samples` 平均;
    外加 `epochs` `(E,)`。小,是 ReDo / dormant 之後要吃的逐神經元活動來源。
  - `full_epoch_XXX.npz` —— 每 `probe_full_every` 個 epoch(0 = 從不)。前
    `probe_full_samples` 筆(預設 2)的完整 `LayerForwardTrace` 四欄 `(S, n, max_steps)`。
    大,給人工 debug 自訂 decoder / 動力學。
- 出界重練退回已記錄過的 epoch 號時,覆寫該列不新增。
- **不動** `metrics.csv` / `checkpoint.npz` / `run.yaml` / `params.npz`;只寫 `traces/`。
- config 旋鈕(`train:` 區塊):`probe_every` / `probe_samples` / `probe_full_every` /
  `probe_full_samples`。

### 7.2 讀端:`example/inspect_traces.py`(已實作)

吃 `<exp_dir>` 或 `<exp_dir>/traces`,印:

- `summary.npz`:每層休眠比例隨探測 epoch 的曲線(用 `spike_count` 或 `s_value_sum`
  當活動量,`--activity`)、首末趨勢、整段沒醒的神經元數、末 epoch 活動量分布 +
  最活躍 / 最安靜前 K 顆、`v_final` 統計 + 非有限計數、`idle_frac` 平均。
  休眠統計直接呼叫 `salt_core/dormant.py` 的 `dormant_score`,用的是同一套歸約;
  數值要跟 `metrics.csv` 的 `dormant_report` 完全對齊,得把 `probe_samples` 設成
  128(`dormant_report` 固定用前 128 筆),否則兩者只是同法不同基數的估計。
- 非會 fire 的層(輸出層 `v_th = 10^9`)在休眠表裡永遠 `dormant_frac = 1.0` /
  `act_p90p10 = nan`,是「這層不 fire」的正確表示,不是壞掉;有意義的是它的
  `v_final`(decoder 輸入)。
- `full_epoch_XXX.npz`(`--full EPOCH`):選一筆樣本(`--sample`)一顆神經元
  (`--neuron`,預設該樣本最活躍的),攤 spike 步、對應毫秒、`v_steps` / `s_value`
  前 20 步;層級印總 spike / fire 神經元數 / 空轉步比例 / `v_steps` 值域 / 非有限計數。

### 7.3 還沒定的

1. **`eval_test` 的 `--trace`:2026-09-11 決定不做。** 原本設想「這裡沒有跨
   epoch 可比、擾動訓練的顧慮,政策問題大半消失」只是講「做起來比較沒包袱」,
   不是「這件事跟跑分數是同一個任務」——`eval_test.py` 的定位就是跑分數
   (accuracy / loss / confusion matrix,已實作,跟這份監測規格是不同關注點,
   不在這裡追蹤),深入分析(某神經元為什麼這樣、畫圖之類)是另一種消費者,
   硬塞進同一支腳本違反「一支檔案只做一件事」。深入分析要做,獨立成一個
   新的 debug 工具,現在沒有
   具體需求,不預先設計。`eval_test.py` 現有的「從 `exp_dir` 重建
   layers/decoder/params」那段(`_load_run_record`/`_rebuild_layers`/
   `_load_params`)以後會是這個 debug 工具的第二個消費者,到時候再決定要不要
   搬進 `example/utils.py`——現在只有一個消費者,不搬。
2. **dormant / ReDo 的逐神經元活動來源:2026-09-11 決定 ReDo 本身先擱置,這裡跟著擱置。**
   討論過程查證:(a) ReDo 是 Sokar et al. 2023 針對 ANN/RL non-stationary target 驗證的方法,
   查無 SNN 場景下「偵測快死神經元、重置權重復活」這個具體流程被驗證過的文獻;(b) 我們的
   conv 權重是整個 output channel 共用一顆 kernel,但活動量是逐 `(channel, 空間位置)` 算,
   兩者粒度不一致,要重置得先決定聚合規則;(c) conv1 直接接原始事件,零放電有兩種不同成因
   ——輸入端根本沒事件掉進來(資料幾何造成,重置無效)vs 輸入有到但權重跨不過門檻(才是
   initialization 造成、reset 有意義的情況)——現在沒有辦法分辨這兩種。(d) 沒有證據顯示現有
   `init_k=5.0` baseline 因為沒有 ReDo 出問題,見 [`TODO.md`](TODO.md)「開放題」:V6 驗證過
   `init_k=√3` 70% 休眠仍訓到 0.795,`init_k=5` 休眠會自己降。真的要疊深網路(尤其 FC→FC)
   再重新評估這整個方向,不是現在就得決定活動來源要怎麼接。
3. **`metrics.csv` 加欄**:從 traces 現場算的純量(dead-step 比例 / 飽和 / `nonfinite`)。
   原本等 ReDo 準則定案再做決定,ReDo 已擱置(見上),這裡一併擱置,避免加沒有消費者的欄
   (§4.2)。
