## 三、決策:不套閘 + soft reset,不是硬 reset

**狀態:✅ 已定案且已實作,不用再考慮。**

比較訓練效果、實作複雜度、執行速度後,決定 fire 判斷不套用 surrogate 修正(沒 fire 的事件維持純仿射)、fire 那一點用 soft reset(`v_final=(1-s_k)x_k`,保留「超過門檻多少」這個梯度訊號,不是直接指定常數 0 切斷梯度)。理由跟完整推導見 `docs/math/不套閘與soft-reset梯度推導.md`。

**這個組合換到的工程好處**:整條計算圖全由 JAX 原生就懂得微分的運算組成(`associative_scan` 上完全沒有套用 surrogate,純仿射,微分規則標準)——不需要手寫 `jax.custom_vjp` 去處理 chunk 化的 fire/reset 邏輯。如果套閘,chunk 化之後「這個 chunk 裡有沒有東西 fire、fire 在哪裡」會變成一個需要手動處理梯度的離散決策點,複雜度高很多。

## 四、洞見:離散索引 gather 不會把梯度帶回「決定索引值的來源」

**狀態:✅ 已定案且已實作(`event_gain` 機制就是這個洞見的解法),純知識性記錄。**

`build_fc_queue`/`build_conv_queue` 用 `event_source_idx`(離散索引)從 `W` gather 權重。這個操作對「被索引的 `W`」有梯度,但不會讓「決定這個索引值的來源」出現在算式裡——不管上一層權重是多少,查出來的都只是 `W` 的某個 column,`jax.grad` 對上一層權重求出來的梯度恆為 0。**這是計算圖裡真的沒有這條邊,不是實作沒寫完整**,任何用離散索引接兩層的地方都會踩到。

修法:`run_layer_forward` 額外回傳 `s_spike`(每個 spike 事件自己 fire 那一刻的可微分強度,forward 精確等於 1,不是視窗內加總值),當成下一層 `build_*_queue` 的 `event_gain` 乘進權重——數值不變,但因為 `s_spike` 是 `atan_spike` 算出來的、對上一層權重有梯度,重新接通這條路徑,跟第三節的 soft reset `(1-s)*v` 是同一個技巧。這正是 `event_gain` 這個參數存在的理由。

## 五、洞見:JAX 負數 index 是 wraparound,不是 clip

**狀態:✅ 已知並已用對策略處理(clip / `mode='drop'`),提醒後人別踩同一個坑,不是待辦。**

conv 的 invalid tap 候選,`k` 算出來可能是負數。原本以為 gather 對負數 index 會 clip 到 0,實際上 JAX fancy indexing 對負數 index 是 NumPy 式 wraparound(`k=-1` 讀到 `W[...,K-1]`)——已實測驗證。任何處理 invalid 候選、假設「負數會被擋下來」的地方都要注意這個坑,scatter 階段一定要用 `mode='drop'` 搭配保證越界的哨兵值,不能靠負數自然擋掉。

## 六、洞見:同一時間戳記排序,用複合鍵不能只用時間

**狀態:✅ 已定案且已實作,不用再考慮。**

多個事件/神經元剛好同時間戳記時,只用 `times` 排序會退化成 `jnp.nonzero`/`argsort` 的攤平順序(等於原始 index),跟真實時間先後無關,而**處理順序會實際影響殘留電位數值**(換順序,同一組輸入最後留在神經元裡的 $V$ 不同)。訓練端排序必須用 `(times, 原始位置)` 複合鍵,才能保證同分時老實照抄「先來後到」,不能假設通用排序函式的預設行為就是對的。

## 七、洞見:$N$(經過的時間差)的計算基準是模擬起始時刻,不是第一筆事件的時間

**狀態:✅ 已釐清且已正確實作,不用再考慮。**

$N = m_i - m_{last}$,$m_{last}$ 初始值是 $t{=}0$,不是「這顆神經元收到的第一筆事件自己的時間」。只有第一筆事件剛好發生在 $t{=}0$ 時兩種算法才會算出一樣的答案,事件從非零時刻開始就會有差異。

## 九、決策:GPU 記憶體用 `XLA_PYTHON_CLIENT_PREALLOCATE=false`,不是別的選項

**狀態:✅ 已定案且已實作(現在設在 `conftest.py`),不用再考慮。**

JAX 預設會預先要一大塊 GPU 記憶體,容易跟其他行程搶、報 OOM。選 `XLA_PYTHON_CLIENT_PREALLOCATE=false`(完全關掉預先要,用多少要多少),而不是 `MEM_FRACTION`(仍預先要,只縮目標)或 `ALLOCATOR=platform`(官方註明非常慢)。

Sources:[GPU memory allocation — JAX documentation](https://docs.jax.dev/en/latest/gpu_memory_allocation.html)、[jax-ml/jax#788](https://github.com/jax-ml/jax/issues/788)

## 十、決策:firing rate 訓練過程單調下降,判斷不是問題、不處理

**狀態:✅ 已定案,不用再考慮。**

觀察到隱藏層 firing rate 訓練全程單調下降到很低值,查證是 surrogate-gradient 訓練 SNN 的已知現象([The fine line between dead neurons and sparsity in binarized SNNs](https://arxiv.org/pdf/2201.11915)、[Training SNNs Using Lessons From Deep Learning](https://arxiv.org/pdf/2109.12894) 第 3.5 節),不是這個專案獨有的 bug。

使用者決策:firing rate 低對這個專案的 FPGA 部署目標本來就是好事(spike 越少代表功耗越低),真正該看的判準是準確率有沒有掉到不能用——沒有,不算真的出問題。文獻提到的緩解手段(threshold annealing、firing-rate regularization)現在不做,等真的需要再評估,且應該做成模型自己選擇性提供的 hook,不焊進通用訓練迴圈。

## 十二、洞見:段 3.8 的 firing-rate 目標帶選出的 init_k,訓練準確率反而較差

**狀態:✅ 已解決(2026-09-08)。** firing-rate 準則廢棄,定案 committed `init_k = 5.0`(三層),不校準。

**洞見(durable)**:在這個資料規模下,「命中 firing-rate 目標帶 `[0.20, 0.50]`」跟「訓練得好」是**背離**的——發放更稀疏反而更準。用 receptive-field 正規化 firing rate 當 init_k 選值準則會把 init_k 推進「單筆事件就 fire」的飽和區(surrogate 斜率崩 + 輸出資訊塌陷 + 事件爆炸 + init loss 條件差)。第十節記過「firing rate 單調下降不是問題」;這一節更進一步:**主動把 firing rate 往上推是有害的**。
