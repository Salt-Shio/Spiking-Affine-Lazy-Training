## 三、決策:不套閘 + soft reset,不是硬 reset

**狀態:✅ 已定案且已實作,不用再考慮。**

比較訓練效果、實作複雜度、執行速度後,決定 fire 判斷不套用 surrogate 修正(沒 fire 的事件維持純仿射)、fire 那一點用 soft reset(`v_final=(1-s_k)x_k`,保留「超過門檻多少」這個梯度訊號,不是直接指定常數 0 切斷梯度)。理由跟完整推導見 `docs/math/不套閘與soft-reset梯度推導.md`。

**這個組合換到的工程好處**:整條計算圖全由 JAX 原生就懂得微分的運算組成(`associative_scan` 上完全沒有套用 surrogate,純仿射,微分規則標準)——不需要手寫 `jax.custom_vjp` 去處理 chunk 化的 fire/reset 邏輯。如果套閘,chunk 化之後「這個 chunk 裡有沒有東西 fire、fire 在哪裡」會變成一個需要手動處理梯度的離散決策點,複雜度高很多。

## 四、洞見:離散索引 gather 不會把梯度帶回「決定索引值的來源」

**狀態:✅ 已定案且已實作(`event_gain` 機制就是這個洞見的解法),純知識性記錄。**

`build_fc_queue`/`build_conv_queue` 用 `event_source_idx`(離散索引)從 `W` gather 權重。這個操作對「被索引的 `W`」有梯度,但不會讓「決定這個索引值的來源」出現在算式裡——不管上一層權重是多少,查出來的都只是 `W` 的某個 column,`jax.grad` 對上一層權重求出來的梯度恆為 0。**這是計算圖裡真的沒有這條邊,不是實作沒寫完整**,任何用離散索引接兩層的地方都會踩到。

修法:`run_layer_forward` 額外回傳 `s_spike`(每個 spike 事件自己 fire 那一刻的可微分強度,forward 精確等於 1,不是視窗內加總值),當成下一層 `build_*_queue` 的 `event_gain` 乘進權重——數值不變,但因為 `s_spike` 是 `atan_spike` 算出來的、對上一層權重有梯度,重新接通這條路徑,跟第三節的 soft reset `(1-s)*v` 是同一個技巧。這正是 `event_gain` 這個參數存在的理由。

## 五、洞見:JAX 負數 index 是 wraparound,不是 clip

**狀態:✅ 已知並已用對策略處理(clip / `mode='drop'`),提醒後人別踩同一個坑,不是待辦。**

conv 的 invalid tap 候選,`k` 算出來可能是負數。原本以為 gather 對負數 index 會 clip 到 0,實際上 JAX fancy indexing 對負數 index 是 NumPy 式 wraparound(`k=-1` 讀到 `W[...,K-1]`)——已實測驗證。任何處理 invalid 候選、假設「負數會被擋下來」的地方都要注意這個坑,scatter 階段一定要用 `mode='drop'` 搭配保證越界的哨兵值,不能靠負數自然擋掉。

## 六、洞見:同一時間戳記排序,用複合鍵不能只用時間

**狀態:✅ 已定案且已實作,不用再考慮。**

多個事件/神經元剛好同時間戳記時,只用 `times` 排序會退化成 `jnp.nonzero`/`argsort` 的攤平順序(等於原始 index),跟真實時間先後無關,而**處理順序會實際影響殘留電位數值**(換順序,同一組輸入最後留在神經元裡的 $V$ 不同)。訓練端排序必須用 `(times, 原始位置)` 複合鍵,才能保證同分時老實照抄「先來後到」,不能假設通用排序函式的預設行為就是對的。

## 七、洞見:$N$(經過的時間差)的計算基準是模擬起始時刻,不是第一筆事件的時間

**狀態:✅ 已釐清且已正確實作,不用再考慮。**

$N = m_i - m_{last}$,$m_{last}$ 初始值是 $t{=}0$,不是「這顆神經元收到的第一筆事件自己的時間」。只有第一筆事件剛好發生在 $t{=}0$ 時兩種算法才會算出一樣的答案,事件從非零時刻開始就會有差異。

## 八、洞見:JAX/XLA 在 GPU 上的規約運算不保證可重現,連同一顆 seed 都不例外 (已修正，把 drop 排掉)

**狀態:⚠️ 2026-09-18 重新打開調查——找到一個候選修法(`vmap`→`lax.map`),但效能代價還沒用完整網路量過,尚未定案,細節見文末「2026-09-18」小節。** 2026-09-04~08 那時的決定(下方維持原文,當歷史記錄)是「不設 determinism flag,接受同一顆 seed 重跑會分岔的代價」——這個決定本身沒有變,只是這次多查到一條路,還沒走到底。

**2026-09-08 重新特徵化(下方 §「2026-09-08」細節),結論收斂成三點,取代舊的「還有兩處沒堵的 gather」說法:**

1. **forward 不受影響**:flag 開/關,`build_conv_queue_compressed` → `run_layer_forward` 的 v_final 逐位元相同(實測 Δ=0,production 幾何、fire / 不 fire、有 / 無 event_gain)。**要跟 CSNN-FPGA 做 bit-exact 硬體驗證,是比對 forward,flag 可以開,這個 bug 打不到。**
2. **flag-on 的梯度 bug 只在訓練期**:觸發條件是「外層 batch `jax.vmap`(batch ≥ 2)+ `jax.grad` + determinism flag」,`ConvNetCompressed.apply_batched` 剛好符合。實測 `dL/dW` 相對誤差 ≈ 0.4–0.5,跟 fire、`event_gain` 都無關;batch=1 完全正常;同樣 batch-vmap 的密集參考實作也完全正常 → 是壓縮版特有路徑(`_compress_candidates` 的 `mode='drop'` scatter,或巢狀 vmap 的 W-gather)在 determinism scatter codegen 下的 transpose 出錯。
3. **flag-off 的非決定性是浮點捨入、不是「算錯」**:量級見下方,實務上 loss 曲線畫出來重疊、最終準確率落在 seed 變異內。

`jnp.sum`/`associative_scan` 這類規約運算,XLA 可以自由選規約順序,浮點加法不滿足結合律。沒開 determinism flag,同一顆 seed、同一份 config 重跑一次,訓練曲線會分岔——不是「seed 沒對齊」,是同一顆 seed 也重現不了([JAX GitHub Discussion #10674](https://github.com/jax-ml/jax/discussions/10674))。~~修法:`XLA_FLAGS=--xla_gpu_deterministic_ops=true`,必須在 `import jax` 之前生效。效能代價量過:+8.8%,可接受。~~

**2026-09-04 這個修法已經推翻,determinism flag 不再設定**(當初設在 `.env`,`.env` 後來整套移除):段 4(`ConvNetCompressed` 等價測試)實測到這個 flag 開著時,`jax.grad` 對 `build_conv_queue_compressed`(`jax.vmap` 對 OC 軸 + gather,非真 tap 位置的 tap index 可能落在 `[0,K)` 之外、靠 gather 的 clip 語意擋)算出**完全錯誤的梯度**(某個真實 tap 的 `dL/dW` 被算成 0,有限差分驗證真正答案是非 0)——forward 數值完全正確,只有反向傳播錯,而且關掉這個 flag 之後同一份程式碼、同一組資料就算對了。查證(當時)認為是已知的 JAX/XLA bug,不是這個專案的程式碼問題,引用了 [jax-ml/jax#25878](https://github.com/jax-ml/jax/issues/25878)(`grad`/`jacrev` + `vmap` + clip 模式的越界索引 → 梯度算成 0,`jacfwd` 正確)、[jax-ml/jax#27796](https://github.com/jax-ml/jax/issues/27796)(`xla_gpu_deterministic_ops=true` 讓索引操作算錯)、[jax-ml/jax#32875](https://github.com/jax-ml/jax/issues/32875)(同一個 flag 搭配 `dot_general` 也有類似問題)三個 issue 當依據(細節見下方 2026-09-05 的修正)。

**段 1(`build_conv_queue_compressed`)既有的 18 項測試,在同一個 flag 開著時全部通過,沒有抓到這個問題**——這類 bug 通常跟具體 shape/vmap 批次大小有關,段 1 測試用的小尺寸 fixture(`H_OUT=W_OUT=3`)剛好沒觸發到會走進錯誤 codegen 路徑的情況,段 4 用 production 尺寸(真正的 conv1 幾何,17×17 輸出)才第一次踩到。**這代表任何用小尺寸 fixture 驗證過的壓縮版佇列邏輯,不能自動假設在 production 規模下、開著這個 flag 時梯度也是對的**,是這次才學到的教訓。

**使用者決策(2026-09-04)**:可重現性不比可用性(梯度正確)重要,拔掉這個 flag,訓練接受同一顆 seed 重跑會分岔的代價。

| 組合 | rel 誤差 | 錯誤分量 |
|---|---|---|
| 無旗標 | 4e-7 | 0/144 |
| 舊 `xla_gpu_deterministic_ops` | 0.231 | 56/144 |

四種**數字 bit-exact 相同**(不是「程度不同的錯」),代表這幾個旗標對這條路徑走進同一段 codegen,不是分析不夠細,是真的沒有旗標層級的解法。

**找到有效的候選修法:外層 batch 改用 `lax.map`,不用 `vmap`。** 同一組 production 幾何,`jax.grad(loss_batched)`(`loss_batched` 內部用 `jax.lax.map` 而非 `jax.vmap` 掃過 batch 軸)在舊旗標開著時,對 batch=1-loop oracle 的 rel 誤差回到 1.3e-7(0/144 錯),等同旗標關掉時的浮點雜訊等級。額外測過「`vmap(grad(...))` 換掉 `grad(vmap(...))`(只調換組合順序,兩者都還是 vmap)」——**沒用**,結果跟 `grad(vmap(...))` bit-exact 相同,證明問題是「這條 batch 軸有沒有被 vmap 過」本身,不是 vmap/grad 疊放的順序。

**代價:單層 conv1、batch=8 的微基準,`lax.map` 比 `vmap` 慢 3.08 倍(50ms vs 16ms/次 `jit` 後的 grad 呼叫)。** 這只是單一 conv 層 + 合成事件的隔離測試,不是完整雙層 conv+FC 網路訓練一步的實測——真正訓練時 batch vmap 佔全部計算圖的比例、以及是否有其他非 batch 相關的優化空間,都還沒量。**這個數字之後如果要拿來當決策依據,必須先在完整網路上重新量,不能直接套用這個單層數字。**

**這次沒有查、還要留意的事**:只測了「整個 loss 都走 `lax.map`」這一種粒度,沒測「只把觸發點附近(`run_layer_forward` 的 backward)包 `lax.map`、其餘計算圖照舊 `vmap`」這種局部化方案,理論上有機會拿到中間的效能/正確性平衡,但工程複雜度高很多(牽涉切開 batch 軸在計算圖中間換維度處理方式),沒實作也沒驗證可行性。

**再往下挖,找到編譯器層級的具體根因(修正 2026-09-08 一項結論):**

先前 2026-09-08 記錄「`sum(build_conv_queue_compressed(...).maps.b)` 單獨 batch-vmap + grad,flag 開著**正常**(rel ~1e-4)→ 佇列建構本身不是觸發點」。**這個結論是錯的,這次修正**:用一模一樣的隔離方式(只測 `build_conv_queue_compressed` 輸出,不接 `run_layer_forward`)在極小案例(`h_in=3` 即既有測試 fixture 同尺寸、`IC=OC=1`、4 筆事件、`batch=2`)重測,一樣壞(rel≈0.33)——連 production 幾何(17×17、400 事件、batch=4)這個組合單獨測都壞(rel≈0.033),只是量級比接了 `run_layer_forward` 之後小,不是真的沒事,是 2026-09-08 那次測試的量級/情境沒踩到門檻。

**幾何大小不是觸發門檻,反而越小錯得越嚴重**(同樣用「batch=1 loop 加總」當 oracle,舊旗標開著,batch=4,conv1 K=3/S=2/P=1):

**且不需要 spike 這條離散分支**:`v_th=1e9`(強制不 fire,只剩純仿射計算)在 `h_in=3, n_events=4, batch=2` 這個極小案例下,rel 誤差仍有 0.454——推翻 2026-09-08「不 fire 時 flag 開/關/FD 三者一致」的結論(那次沒有把「不 fire」跟「外層 batch vmap」這兩個條件同時湊在一起測)。

**縮到 `build_conv_queue_compressed` 單獨測、`h_in=3、IC=OC=1、4 筆事件、batch=2` 這個最小案例,dump 編譯後的 HLO(`jax.jit(...).lower(...).compile().as_text()`)比對旗標開/關,找到具體差異,鎖定同一個 `scatter-add` instruction**(對應 `_compress_candidates` 的 scatter 被反向傳播轉成 `transpose(jvp(vmap(vmap())))/scatter-add`,`vmap(vmap())` 正是「佇列建構內部既有的 vmap」疊上「這次新加的外層 batch vmap」兩層):

- 旗標關(對):`scatter_dims_to_operand_dims={1,2,3}`
- 旗標開(錯):`scatter_dims_to_operand_dims={1,2,3,0}`,且多宣告了 `indices_are_sorted=true, unique_indices=true`

**兩個問題都具體、可驗證**:scatter 目標是 rank-4 的 `f32[1,1,3,3]`,只該 scatter 進 3 個維度,旗標開著時維度列表多塞了一個 `0`,是結構性的維度標記錯誤;`unique_indices=true` 這個宣告本身就是假的——`_compress_candidates` 刻意用重複的 sentinel index 標記「無效候選」(見第 5 節「JAX 負數 index 是 wraparound」跟這裡是同一類「候選不合法時用哨兵值」設計),這些 index 天生不唯一。

**目前的根因判斷(codegen 層級,不是這個專案的邏輯錯誤)**:XLA 的 GPU determinism scatter-rewrite pass("scatter determinism expander",官方文件描述會為效能把某些 scatter 走快速路徑)套用在「由巢狀 `vmap(vmap())` 的反向傳播(transpose of jvp)產生」的 scatter-add 上時,維度標記算錯、且錯誤地假設索引唯一,選了一條只在索引真的唯一時才正確的快速路徑——這個專案的資料不滿足這個前提,結果就是部分梯度分量被錯誤地覆蓋/丟棄而非正確累加。跟第八節最上面 2026-09-04 引用的三個 issue(#25878/#27796/#32875)同屬「vmap + gather/scatter + grad + determinism flag」這個大家族,但這次定位到具體是哪個 instruction、哪兩個欄位錯,比之前任何一次都精確。**還沒做的事**:寫成不依賴這個專案任何程式碼的純 XLA/HLO 或純 JAX 最小重現(這次的 repro 仍然 import 了 `salt_core.connectivity.conv`),決定要不要往 jax-ml/jax 或 openxla/xla 報 issue。

診斷腳本沒進 repo(`/tmp` 底下,session 結束會消失),之後若要重跑驗證,查詢方法/幾何參數/HLO diff 方法照上面複現即可,不算複雜。**這次獨立整理成不依賴這個專案程式碼的最小重現,進了 `xla_repro/`(`repro.py`/`dump_hlo.py`/`README.md`/HLO 文字檔),之後要重跑或要送 issue 直接用那份。**

`jax.vmap(lambda oc_w: oc_w[c_g, safe_k_y, safe_k_x])(W)` 跟廣播式花式索引 `W[:, c_g, safe_k_y, safe_k_x]` 數值完全等價(`xla_repro/test_no_inner_vmap.py`),把 `xla_repro/repro.py` 改成後者、拿掉這一層顯式 vmap 呼叫,**bug 照樣重現,數字沒變**。這推翻「兩層顯式 vmap 疊加」是觸發條件的假設——真正的必要條件比這更深,可能跟 gather 用的 index 陣列本身是不是「由 `_compress_candidates` 的 `lexsort`+`cummax`+scatter 這條鏈算出來的追蹤值,而非直接常數輸入」有關,還沒進一步驗證。**結論:目前找不到能靠改寫這個專案程式碼繞開的方法,已知有效的只有把外層 batch 從 `vmap` 換成 `lax.map`(見上方,代價是變慢,真實開銷還沒在完整網路量過)。**

**2026-09-18 續查,徹底推翻「`vmap` 是觸發條件」這個假設,關掉「自己做向量化」這條路(不用再回頭試)**:

用 `example/models/conv_net.py::apply_batched` 把 `jax.vmap` 換成 `jax.lax.map` 之後,單層合成 benchmark 量到 batch=8 時慢 5 倍、batch=16 時慢 7.24 倍(隨 batch 幾乎線性成長,不是固定倍率——`lax.map` 底層是 `lax.scan`,沒有把 batch 軸融合進向量化運算,每個樣本依序各付一次 kernel 排程開銷;`vmap` 是真的融合,GPU 沒被餵飽時 batch 越大越划算)。**加上旗標本身就讓 vmap 慢 3.6 倍(officially 文件講的「開 determinism 關掉某些高效能 kernel/融合優化」代價),兩者疊乘,`lax.map`+開旗標 對比 `vmap`+不開旗標 是 10.3 倍慢**,不是先前單獨量 `lax.map` vs `vmap`(兩者都開旗標)看到的 3 倍。

因此追問「能不能自己手動向量化(不靠 `jax.vmap`,批次軸直接塞進 `_compress_candidates` 的排序/scatter 目標維度,像 OC 軸那樣用廣播處理)」,理論基礎是 `run_layer_forward` 自己內部那層 vmap(掃 neuron 軸)已證實安全(見上面「run_layer_forward 单独测」那段),如果 `build_conv_queue_compressed` 能把 batch 也用廣播塞進去、輸出直接攤平成 `(batch×OC×H_out×W_out, L)`,下游完全不需要知道那個 leading axis 代表 batch 還是 neuron。

**做出這個「完全不呼叫 `jax.vmap`」的版本(`xla_repro/test_no_vmap_batch.py`/`test_no_vmap_customvjp.py`,batch 折進 `_compress_candidates` 的複合排序鍵跟 scatter 目標維度、weight gather 全部用廣播),production 尺寸(17×17、400 事件、batch=8)測試,旗標關掉逐位元正確,**旗標開著一樣錯(rel≈0.035,跟先前用 `custom_vjp` 手寫 backward 搭配 outer vmap 量到的殘留誤差完全同一個數字)**。進一步排除:連 `custom_vjp` 手寫的 `jax.lax.scatter_add`(自己指定正確的 dimension_numbers,不依賴 autodiff 產生的版本)包在這個完全無 vmap 的版本裡,**一樣錯,數字不變**。

**結論(定案,不用再回頭試自己動手向量化)**:真正的觸發條件不是 `jax.vmap` 這個 transform 本身,是「一個 `scatter-add` 呼叫裡,索引來自兩個以上邏輯獨立的樣本、需要合併累加」這件事——不管是透過 `vmap` 自動疊、還是手動把 batch 攤平進同一份 index list,只要合併進同一次 scatter 呼叫就會被這個 XLA bug 咬到。`lax.map` 能算對,不是因為它不用 `vmap`,是因為它讓每個樣本的 scatter **從不合併**、各自獨立呼叫——這是目前唯一已知,同時滿足「開著 determinism flag」+「梯度正確」的結構性條件。只要這個 XLA/XLA-GPU 層級的 bug 沒有上游修掉,**沒有任何程式碼寫法能把這條路徑做成單一 kernel 呼叫的真正向量化**,`lax.map`(或效能一樣、Python 手動展開迴圈——兩者實測速度幾乎相同,`xla_repro/timing_unroll.py`)是唯一選項,10.3 倍的效能代價是這個選項的真實成本,不是還沒找到更好寫法。

**2026-09-18 再往下拆,更正上一段「合併多樣本進同一次 scatter 就會壞」這個講法太寬,補上真正的必要條件(不是只有 batch 合併)**:

上一段的驗證方法是「從確認會壞的完整版本改寫」,但沒有反向驗證「拿掉某個成分之後,單純的 batch 合併本身夠不夠」。這次補做:寫一個更簡化的版本(用常數 index 陣列,不經過 `_compress_candidates` 的 `lexsort`/`cummax`,直接給定重複的 index),BATCH=1~4、旗標開關都測——**完全正確,bug 沒有出現**。把 `_compress_candidates` 的 `lexsort`+`cummax`+scatter 加回來,但拿掉 `_axis_candidates` 那段 conv 幾何(候選用隨機亂數產生,不是滑動視窗公式算出來的)——**還是完全正確**。這兩次「重建的簡化版」都測不出 bug,代表「多樣本合併進同一次 scatter」本身不是充分條件,上一段的結論下得太早。

**改用正確的拆解方法:從已經確認會壞的完整版本(`xla_repro/test_no_vmap_customvjp_small.py`,H_IN=5、BATCH=1 對/BATCH≥2 錯)開始,一次只拿掉一個成分,每步都旗標開關各測一次**:

1. 拿掉「無效欄位蓋成 0」的 mask(`_affine_with_catchup` 對應的 is_real 遮罩)——**還是壞**(rel 變小,但 BATCH≥2 依然錯),mask 不是必要成分。
2. 把 `_axis_candidates` 的 2D(y、x 兩軸)簡化成只留 y 軸的 1D——**還是壞**,2D 交叉結構不是必要成分。
3. 拿掉「候選可能不合法、需要用 sentinel 標記、靠 scatter `mode='drop'` 丟棄」這個機制(讓所有候選都直接視為合法,不丟棄任何一筆)——**bug 完全消失**,BATCH 1~4、旗標開關全部正確。

**真正的必要條件(兩者缺一都不會觸發,兩者合起來已用逐步拆解驗證)**:
1. 合併多個邏輯獨立樣本進同一次 `scatter-add`(上一段已驗證的部分,單獨不夠)。
2. **`_compress_candidates` 有候選被標成不合法、經 `mode='drop'` 丟棄,導致該神經元的壓縮佇列有「未寫入」的空欄位**——`build_conv_queue_compressed` 用 `safe_j = jnp.minimum(local_to_global_j, effective_n_events - 1)` 把這些空欄位(初始化值恆為 `n_events`,不管哪個空欄位都是同一個值)全部夾到**同一個固定的 fallback index**。多個空欄位收斂到同一個 index,是真正的碰撞來源——不是「隨便兩個 index 剛好相同」這種泛用的重複,是這個特定「靠 `.minimum` 夾到同一格」的形狀。

**跟原本專案程式碼的對應**:`salt_core/connectivity/conv.py::build_conv_queue_compressed` 的 `safe_j = jnp.minimum(local_to_global_j, effective_n_events - 1)`(見該函式第 336 行附近,註解裡原本就說明這一步是為了讓夾到的位置「保證是有意義的真實時間,不會拿到天文數字」)——這個安全網本身的邏輯沒有錯(是為了防呆,不是這次 bug 的根因),但它產生的「大量空欄位夾到同一格」這個副作用形狀,剛好是 XLA 那個 determinism scatter-rewrite pass 算錯的觸發模式。

**還沒驗證的事(下一步)**:這次的拆解全部在 H_IN=5 的極小尺寸做,還沒在 production 尺寸(17×17、400 事件)重新走一次同樣的拆解確認同一個結論成立;也還沒實際設計、驗證修法(讓空欄位各自夾到不同的 fallback index,而不是全部夾到同一格,理論上能避開這個碰撞形狀,但要先在小尺寸驗證有效、再上 production 尺寸驗證、最後才能考慮拿掉 `lax.map`、換回 `vmap`)。

## 九、決策:GPU 記憶體用 `XLA_PYTHON_CLIENT_PREALLOCATE=false`,不是別的選項

**狀態:✅ 已定案且已實作(現在設在 `conftest.py`),不用再考慮。**

JAX 預設會預先要一大塊 GPU 記憶體,容易跟其他行程搶、報 OOM。選 `XLA_PYTHON_CLIENT_PREALLOCATE=false`(完全關掉預先要,用多少要多少),而不是 `MEM_FRACTION`(仍預先要,只縮目標)或 `ALLOCATOR=platform`(官方註明非常慢)。

Sources:[GPU memory allocation — JAX documentation](https://docs.jax.dev/en/latest/gpu_memory_allocation.html)、[jax-ml/jax#788](https://github.com/jax-ml/jax/issues/788)

## 十、決策:firing rate 訓練過程單調下降,判斷不是問題、不處理

**狀態:✅ 已定案,不用再考慮。**

觀察到隱藏層 firing rate 訓練全程單調下降到很低值,查證是 surrogate-gradient 訓練 SNN 的已知現象([The fine line between dead neurons and sparsity in binarized SNNs](https://arxiv.org/pdf/2201.11915)、[Training SNNs Using Lessons From Deep Learning](https://arxiv.org/pdf/2109.12894) 第 3.5 節),不是這個專案獨有的 bug。

使用者決策:firing rate 低對這個專案的 FPGA 部署目標本來就是好事(spike 越少代表功耗越低),真正該看的判準是準確率有沒有掉到不能用——沒有,不算真的出問題。文獻提到的緩解手段(threshold annealing、firing-rate regularization)現在不做,等真的需要再評估,且應該做成模型自己選擇性提供的 hook,不焊進通用訓練迴圈。

## 十二、洞見:段 3.8 的 firing-rate 目標帶選出的 init_k,訓練準確率反而較差

**狀態:✅ 已解決(2026-09-08)。** firing-rate 準則廢棄,定案 committed `init_k = 5.0`(三層),不校準。

**洞見(durable)**:在這個資料規模下,「命中 firing-rate 目標帶 `[0.20, 0.50]`」跟「訓練得好」是**背離**的——發放更稀疏反而更準。用 receptive-field 正規化 firing rate 當 init_k 選值準則會把 init_k 推進「單筆事件就 fire」的飽和區(surrogate 斜率崩 + 輸出資訊塌陷 + 事件爆炸 + init loss 條件差)。第十節記過「firing rate 單調下降不是問題」;這一節更進一步:**主動把 firing rate 往上推是有害的**。

V6 實測(10 epoch、同 seed):`init_k` 5 ≈ √3(Lee 變異數保持)≈ 0.80 > 8/8 ≈ 0.765 > 8/64(舊準則)≈ 0.735。完整推導(膜電位穩態變異數 → 命中帶必然飽和 → surrogate 斜率崩 → Lee 變異數保持準則)+ 數值驗證 V1–V6 見 [`math/初始權重尺度推導.md`](math/初始權重尺度推導.md)。

## 十三、洞見:`max_out_spikes` 跟 `max_steps` 是同一個數學量,這次只接了一半

**狀態:❌ 已嘗試接上,實測後撤回——`Σm*` 這個方向不成立,細節見「§十四」,
不要重做。**

`spike_step_upper_bound`(`salt_core/core.py`,推導見
[`math/掃描步數上界推導.md`](math/掃描步數上界推導.md))內部算的 `m*`
(第 3、3.5 節,推論 2/推論 4 原文就叫它「spike 數上界」/「全域 spike 數上
界」),**不是**這次拿去用的「掃描步數上界 `T`」本身——`T = m* +
⌈(L-m*)/chunk_size⌉` 是從 `m*` 再往下推一步才得到的東西。`m*` 本身就是
「這顆神經元整條佇列跑下來最多 fire 幾次」的證明上界,一層所有神經元加總
起來,理論上正是這批資料下 `max_out_spikes` 該有的上界——不是巧合,
`salt_core/layer_chain.py` 的 `_select_spikes` 原本就有 `max_total_spikes`
沒給時的預設值 `n_source_neurons * max_steps`,註解直接寫「恆安全(每顆神經
元每步最多一個 spike)」,這正是同一族推理裡最鬆的版本。

**現況(這次改動之後)**:`spike_step_upper_bound` 算完 `m*` 只拿去推
`T`,函式只回傳 `T`,`m*` 本身沒有往外流出;`ConvLayer.max_out_spikes`
因此還停在改動前的純被動成長(`grown_to_fit` 裡的 `_grow`,觀察
`n_out_spikes` 超過現有容量才長),既沒有用 `m*` 主動估一個證明過的上界,
也沒有 `max_steps` 這次才加上的縮小路徑(`shrink_max_steps`)。這也是
「用量遠低於容量、卻完全不會往下調」的部分原因(另一半原因是 `L` /
`max_out_spikes` 現在結構上根本沒有任何縮小機制,見 `TODO.md`「L 收縮機
制」)。

**之後要處理**:讓 `spike_step_upper_bound`(或新加一個函式)把 `m*` 也
回傳出來,不只是 `T`;`ConvLayer.forward` 對一層所有神經元加總 `m*` 當這批
的 `max_out_spikes` 證明上界,比照 `max_steps` 這次的模式接上「長大用安全
網、縮小用重估」。

**開放題**(串更大網路時再討論)搬到 [`TODO.md`](TODO.md):`init_k = √3` + ReDo 當一個 package,讓冷 init 撐得起會休眠的深層(尤其 FC→FC)。

## 十四、洞見:`max_steps` 不能拔掉 `m*`,`max_out_spikes` 不能再用它——兩者不是同一種問題

**狀態:✅ 已驗證、已定案。**

接續「§十三」:把 `m*` 加總(`Σm*_i`,`docs/math/掃描步數上界推導.md` 第5節
推論5)接進 `ConvLayer.grown_to_fit`/新加的 `shrink_max_out_spikes`,完整跑
過 `example/tests/test_train_conv_compressed.py` 後發現:8 個測試裡 7 個壞
掉,全部同一個成因——剛初始化、還沒訓練的權重下,`Σm*_i` 算出來的值遠比
真實輸出 spike 數大一大截(例如某 batch:`Σm*_i=90185`,但整個訓練過程量到
的真實峰值只有 `21706`),把原本「容量給夠大就不該出界」的既有不變量全部
打破,變成一開始就誤判出界、整個重來。

**根因**:`m`(推論2)的假設是「每個正號權重事件都各自足以獨立造成一次
fire」。這個假設只有在單一權重量級遠大於門檻時才接近成立;這個專案委定的
`init_k=5.0`(見 `docs/規格書.md`)換算出來的單一權重量級(`conv2`
`≈0.59`)反而比門檻(`v_th=1.0`)還小——真實情況通常要好幾個事件疊加才夠
一次 fire,`m*` 系統性地遠大於真實 fire 數。單一神經元已經鬆,`Σm*_i` 是把
這個鬆度對 `N` 顆神經元線性加總,沒有任何機制把誤差壓回去。

**為什麼 `max_steps` 用同一個 `m*` 卻沒事**:`max_steps` 用的是
`T=m*+⌈(L-m*)/\text{chunk\_size}⌉`,不是 `m*` 本身,也不是加總。`T` 對
`m*` 的敏感度只有 `(1-1/chunk_size)` 這個係數(`chunk_size=1` 時甚至完全
抵消,`T` 恆等於 `L`,見「§掃描步數上界推導.md」第4節),而且 `T` 天生被
`L` 封頂,不會因為 `m*` 被高估就無限放大。`Σm*_i` 沒有這個結構——同一個
`m*`,一個用法穩定、一個用法會炸,不是巧合,是公式結構本身的差異。

**更深一層,`max_steps` 為什麼一開始就必須靠 `m*` 撐,不能像 `L`/
`max_out_spikes` 一樣改用純經驗值**:`L`/`max_out_spikes` 出界是「真實資料
裝不下」的被動事實——不管容量設多少,真實需求量(`cq.n_real_events`/
`out_stream.n_real_events`)都能照樣算出來,跟容量設定本身無關,所以能直接
拿真實觀察值當長大/縮小依據(`n_out_spikes`)。`max_steps` 不是被動限制,
是掃描**步數**本身:設太小,`lax.scan` 提早停止,神經元該 fire 卻還沒掃到
就被切斷——不是「東西被截斷但看得出來」,是**靜默算錯**,而且沒辦法事後從
結果反推「其實需要幾步」,因為根本沒跑那幾步。也就是說,`max_steps` 沒有
一個天然、不靠任何理論保證就能直接量出來的「這批資料真正需要幾步」的經驗
值——這正是當初(`docs/math/掃描步數上界推導.md`)必須推導 `m*`/`T` 這個
證明過的上界的原因,不是隨意的設計選擇。

**結論**:`max_out_spikes` 的長大/縮小退回只用 `n_out_spikes`(這次的
`out_spikes_bound`/`shrink_max_out_spikes`/`fire_count_bound` 全部復原、
移除);`max_steps` 繼續用 `m*`/`min_steps_needed`,不動、也不能拔掉。
`docs/math/掃描步數上界推導.md` 第5節推論5/推論6 保留當數學紀錄(仍是正確
的證明),但不接進任何行為邏輯。

## 十五、洞見:訓練中期梯度突然爆炸

**狀態:** ⚠️ 現象確認;根本原因(Edge of Stability,曲率逼近 $2/\eta$)有一階實證支持,細部觸發機制(Adam/batch 對齊)仍待查,見文末對照表。

**實驗來源:** `maxsteps_verify_20260916_121312`(`archive/configs/verify_maxsteps.yaml`,2026-09-28 已刪除,見 git 歷史 `59d292f`;設定快照在該 run 的 `run.yaml`;100 epochs,`weight_snapshot_every=1`,逐 epoch 有完整權重快照)。

### 現象:不是單一事件,是反覆發生的循環

100-epoch 長跑最完整:epoch38 是這次 run 的最佳點(`train_loss=8.9e-5`、`val_accuracy=0.815`),之後反覆炸開又部分恢復:

| 爆炸點 | train_loss(炸前→炸開) | val_accuracy(炸前→炸開) |
|---|---|---|
| epoch38→39 | 0.00009 → 0.340 | 0.815 → 0.575 |
| epoch48→49 | 0.010 → 0.064 | 0.785 → 0.745 |
| epoch62→64 | 0.003 → 0.288 | 0.765 → 0.660 |
| epoch73→75 | 0.012 → 0.108 | 0.695 → 0.610 |

epoch81 之後進入連續惡化、不再恢復,epoch99 收在 `val_accuracy=0.555`,遠低於 epoch38 的峰值。**每次重跑(60、100 epoch)爆炸的確切時間點都不一樣**(GPU 浮點非決定性),但反覆爆炸這個模式本身穩定出現。

**已排除:** 動態放大/出界重跑觸發——每次爆炸的前後,容量欄位(`max_event_queue`/`max_layer_spikes`/`max_steps`)都沒變;容量縮小是爆炸**之後**才發生(活躍度崩潰的結果,不是原因,例如 epoch39 炸完,conv1 容量在 epoch41 才從 5351 縮到 2627)。

### 數學推導

1. $\partial L/\partial z_i=p_i-\mathbb{1}[i=y]$,恆界在 $[-1,1]$,不會爆。
2. 但 $p_y\to1$ 需要 logit 差距 $\Delta$ 無界增長、投報率遞減。epoch38 的 loss 反推 $\Delta\approx9.3$。decoder 是 `membrane_regression`(`v_th=1e9`),輸出無 bounded activation,$\Delta$ 沒有上限。
3. 仿射遞迴(`salt_core/core.py` 的 `combine`)是**收縮**的:$a_k=(1-1/\tau)^{n\_ms}\in(0,1]$ 只跟時間有關、跟權重無關,$\partial v_n/\partial b_i=\prod_{k>i}a_k\le1$,不會透過時間放大梯度。*(訂正討論初期「長時間積分放大梯度」的錯誤猜測。)*
4. 真正可能放大的是**加總項數**:同一個權重可能因多次觸發被重複使用,$\partial z/\partial w=\sum_i\prod_{k>i}a_k$,每項 $\le1$,但項數隨樣本觸發次數增加。
5. `conv2_grad_norm` 是均值,epoch38→39 從 0.0005 衝到 0.48(約 1000 倍),反推必有少數 batch 算出遠超此值的離群梯度。

### 假說演進:離群樣本 → Edge of Stability

**排除:**
- 單一離群 batch/樣本——用爆炸前一刻(epoch38)的權重對全部 1000 筆樣本 forward,沒找到離群 loss/spike 樣本。
- 樣本事件數特別多——資料集把每筆樣本截斷到 2000 筆事件(`docs/規格書.md`),樣本間無差異可言。

**目前假說:Edge of Stability。** loss→0 時曲率(sharpness)持續變陡,超過 $2/\eta$ 門檻就震盪炸開,掉回門檻下又恢復——不需要離群樣本,吻合兩次都找不到兇手的結果;也吻合上方「反覆發生的循環」現象。

**與第 4 點加總項數的可能連結(未驗證):** conv2 `firing_rate` 在每次炸開前持續爬升、炸開瞬間崩落、下一輪再爬升,時間點跟爆炸週期吻合。`firing_rate` 上升代表下一層權重被觸發次數增加,呼應第 4 點推導,但未實測曲率驗證此連結。

**驗證:權重軌跡直接量到放大訊號,不需要 Hessian。**
- 逐 epoch 權重量級 ‖W‖:平原期(訓練接近收斂、梯度小)後接一個跳階,四次跳階時間點全部對上四次爆炸。
- 線性穩定性分析可以推出 $\Delta\theta_{t+1}/\Delta\theta_t\approx(1-\eta\lambda)$(記 $\Delta\theta_t=\theta_{t+1}-\theta_t$ 為實際觀察到的權重步長),不需要碰二階微分。實測這個比值在四次爆炸都明顯放大:epoch38→39 高達 28 倍,其餘三次落在 2~4 倍;其餘 epoch 的比值都在 0.3~2 之間,屬正常波動。
- 曾嘗試直接量測 Hessian 最大特徵值,發現這條路對這個架構走不通:spike surrogate gradient 用 `custom_vjp`(forward 是精確 heaviside、backward 借用另一條平滑曲線近似),二階微分沒有唯一定義——用有限差分交叉驗證,不同算法算出的「二階導數」互相對不上(差異可達 100% 以上)。這是架構本身的限制,不是實作問題,曲率驗證因此改用上面的權重步長比值,不直接碰 Hessian。

Sources:[Gradient Descent on Neural Networks Typically Occurs at the Edge of Stability](https://arxiv.org/pdf/2103.00065)、[Adaptive Preconditioners Trigger Loss Spikes in Adam](https://zhiweibai.github.io/pub/loss_spike.pdf)

### 候選觸發機制與解法

Edge of Stability 是根本原因;下表是「邊緣上那一下怎麼被觸發」的候選機制,彼此不互斥。

| 候選原因 | 怎麼查 | 怎麼改 |
|---|---|---|
| 輸出無上限,$\Delta$/曲率無界增長(根本原因) | ✅ 已驗證:‖W‖ 曲線 + 權重步長比值 $\Delta\theta_{t+1}/\Delta\theta_t$,四次爆炸都是離群放大(Hessian 直接量測因 surrogate gradient 二階微分無唯一解,對這個架構不可行) | label smoothing(限制 $\Delta$)、weight decay(限制權重量級) |
| Adam 用 `β2=0.999` 預設值,沒特別調過,記憶視窗過長,長期小梯度後對稍大梯度正規化過度放大 | 用 epoch38 權重重放 epoch39 該 batch,比對 Adam 更新量 vs raw gradient | 調低 `β2`,或直接 gradient clipping |
| batch 內多個普通樣本梯度方向一致,平均後變大 | 用 epoch38 權重對 epoch39 全部 250 個 batch 各自算真實梯度範數,看是否偏離其他 batch | 加大 batch size 稀釋巧合(改動訓練設定較大) |
| 沒有 gradient clipping,以上任一成立都無阻擋(已確認事實) | 不用查 | 加 `optax.clip_by_global_norm`,成本最低 |

不處理也是選項:訓練迴圈已有 `best_params`,炸開後半段不影響最終交付的權重。

## 十六、解法驗證(2026-09-18):weight_decay + 餘弦退火是目前最佳組合,score_cap 沒有幫助

**狀態:** ✅ `weight_decay=1e-2` + 餘弦退火(`train.lr_cosine_decay`)已重複驗證兩次,結果一致,是目前唯一同時做到「跨重跑穩定」+「明顯改善」的組合。`grad_clip_norm`/`label_smoothing_alpha` 已撤除(見下)。`score_cap` 單獨測試結果不穩定,疊加在 `weight_decay+cosine` 上沒有額外幫助,細節見下方。

### 三個機制各自的驗證結果

| 機制 | 層級 | 驗證次數 | 結果 |
|---|---|---|---|
| `label_smoothing_alpha` | 根因層(改目標) | 1 次(單獨) | 大量神經元死亡(`dormant_frac`→0.9+),最後 `max_out_spikes` 縮到 0 直接 crash(縮小沒有下限保護,這是獨立於本問題的結構性 bug;2026-09-27 架構審查階段 5.1b 已修,縮小的候選值至少是 1)。**已撤除,程式碼不再保留** |
| `grad_clip_norm` | 症狀層(限步伐) | 1 次(單獨,`grad_clip_norm=10.0`);另外疊加在 `weight_decay+cosine` 上跑過 1 次 | 單獨:後期一樣爆炸,只限住單步位移,沒治到曲率持續變大這個根因,不能單獨扛(見 `archive/configs/verify_weight_decay_cosine_grad_clip.yaml` 檔頭,2026-09-28 已刪除,見 git 歷史 `59d292f`)。疊加那次的結果沒有記錄。**已撤除** |
| `weight_decay` | 根因層(限權重量級) | `1e-4`(拉力不足,全程僅 2.5% 累積衰減)、`1e-2`×2(獨立跑兩次) | `1e-2`:沒有死亡風險,擋住不可逆崩潰,但沒有消除震盪本身——`step_ratio` 反彈均勻分布在整個訓練過程,包括接近結尾的 epoch |
| `score_cap=6.0` | 根因層(限輸出上限) | 2 次(獨立) | **結果不穩定**:第一次全程健康(`val_accuracy` 均值 0.780);第二次 epoch73 反彈(7.8倍)後 conv1 spike 數從 941 流失到 138,收尾 `dormant_frac` 衝到 0.93/0.97,近乎死亡 |

### weight_decay 為什麼不會像 label_smoothing 一樣死亡

這個 SNN 的 firing rate 訓練過程本來就有自然衰減傾向(第十節),原本靠「一定要更準確分類」這個壓力撐住。`label_smoothing` 直接調低這個壓力(全域性,不管樣本目前準不準都打折);`weight_decay` 完全不碰這個壓力,只是額外對權重量級加一個獨立的拉力——這是它沒有觸發死亡崩潰的原因。`score_cap` 的 `tanh` 飽和被懷疑也在局部削弱這個壓力(神經元一旦被反彈撞離門檻、往負向飽和,修正的梯度也跟著被削弱),機制上跟 `label_smoothing` 類似但只在飽和區生效,這可能是它結果不穩定(有時觸發、有時不觸發)的原因,**但沒有直接量測過飽和事件本身,這段是推理不是確認**。

### 為什麼加了餘弦退火之後 weight_decay 才真正穩定

穩定條件是 $\lambda_i \le 2/\eta$。`weight_decay` 只能拖住 $\lambda_i$ 的成長,不能把它釘死在上限以下;$\eta$(學習率)全程固定的話,門檻 $2/\eta$ 也全程固定不會變寬,$\lambda_i$ 只要訓練夠久,還是有機會再次逼近這條線——這正是「`weight_decay` 單獨測,反彈均勻分布在整個訓練過程,不會隨時間變少」的原因。餘弦退火讓 $\eta$ 隨訓練進行下降,$2/\eta$ 隨訓練進行升高,補上這一側。

**實測(`weight_decay=1e-2` + `lr_cosine_decay`,獨立跑兩次):**

| | #1 | #2 |
|---|---|---|
| best val_accuracy | 0.835 | 0.850 |
| 全程平均 | 0.799 | 0.810 |
| 最後 20 epoch 平均 | 0.806 | 0.830 |
| 最低點 | 0.675(epoch0) | 0.675(epoch0) |

兩次都只有一次前中段反彈(發生在退火還沒退多少的階段,cosine 曲線頭尾平、中段陡,epoch29/50 時 $\eta$ 大約還在原始值的 8 成左右),**epoch70 之後完全沒有顯著反彈**,`conv1_firing_rate` 全程穩定在 `conv2_firing_rate` 之上(沒有出現「conv1 流失、conv2 代償」那個不對稱模式,見下一段)。最後 20 epoch 平均 val_accuracy 0.806/0.830,是所有測過的組合裡最高的。

### 加 score_cap 疊加(三合一)沒有幫助,可能還輕微扯後腿

同一份 `weight_decay+cosine` config 疊加 `score_cap=6.0`,獨立跑兩次,跟不含 `score_cap` 的兩次對照:

| | 最終權重 norm(conv1/conv2/out) | `step_ratio` 顯著反彈次數 | 最後 20 epoch 平均 |
|---|---|---|---|
| 不含 score_cap #1 | 6.41 / 14.32 / 70.88 | 1 | 0.806 |
| 不含 score_cap #2 | 6.47 / 15.59 / 71.63 | 1 | 0.830 |
| 含 score_cap #1 | 6.87 / 16.25 / 76.27 | 2 | 0.859 |
| 含 score_cap #2 | 6.78 / 16.11 / 72.52 | 2 | 0.802 |

**最後 20 epoch 平均這個指標,兩組範圍重疊(0.806~0.830 vs 0.802~0.859),雜訊蓋過差異,分不出好壞。** 但另外兩個指標兩組各自的 2 次都完全一致、沒有重疊:含 `score_cap` 的反彈次數穩定多 1 次;最終權重量級三層(conv1/conv2/out)全部一致地更大。後者尤其違反 `score_cap` 的設計初衷(理論預期是限制輸出、間接讓權重不用長那麼大)——懷疑是 `tanh` 飽和後,同樣的底層權重變化量能反映到輸出分數的比例變小,網路要達到同樣效果反而要把權重推得更大來補償,但這是推理,沒有直接驗證。

**結論:`score_cap` 目前沒有理由疊加在 `weight_decay+cosine` 上,主線用 `weight_decay+cosine` 兩個機制。**

### conv1 vs conv2 firing rate 不對稱:震盪的下游後果,不是架構天生如此

原始無修正跑法四次爆炸,`conv1_firing_rate` 每次都降、`conv2_firing_rate` 多數時候升(尤其後兩次),長期趨勢是 conv1 一路下滑、conv2 一路上升。機制推理(未直接驗證):

1. conv1 離 loss 較遠(`loss → out → conv2 → conv1`),梯度要多穿過一層 conv2 的 surrogate gradient,訊號天生比 conv2 弱。
2. `salt_core/surrogate.py` 的 ATan surrogate 梯度公式 $\frac{\alpha/2}{1+(\frac{\pi\alpha}{2}x)^2}$($x$=膜電位離門檻距離)離門檻越遠衰減越快,conv1 神經元一旦被震盪撞遠,修正訊號又更弱。
3. 兩個削弱疊加,conv1 被撞遠後修不回來,fire 越來越少;conv2 訊號較強、被推去代償上游變少的刺激,fire 上升。

`weight_decay+cosine` 那兩次乾淨跑法裡,`conv1_firing_rate` 全程穩定在 `conv2_firing_rate` 之上,沒有出現這個不對稱——支持「這個不對稱是震盪的下游後果,不是架構天生的宿命」:把震盪本身壓下去,這個模式也跟著消失。但三合一疊加 `score_cap` 那兩次,`conv2_firing_rate` 從中段開始持續略高於 `conv1_firing_rate`,而 conv1 自己的絕對活動量仍穩定成長、`dormant_frac` 沒有崩潰——**修正判準**:conv1/conv2 交叉本身不是關鍵,conv1 自己的絕對活動量有沒有在下滑才是;良性交叉(兩層都健康、只是相對強弱不同)不等於惡性交叉(conv1 死亡、conv2 代償)。

## 十七、決策:膜電位量化的 $a$、$b$、$v_{th}$ 在整數尺度算,不在物理尺度

**狀態:✅ 已處理。** 整數版 forward 的膜電位暫存器、權重碼、門檻都是整數。
下面描述的「目前的實作」是改之前的做法,留著說明為什麼不能在物理尺度上模擬:
目標是跟 FPGA 逐位元一致,「數學上等效」不夠。

膜電位量化推導文件的遞迴式,是在縮放過的尺度上寫的:

$$\tilde V_k = r(a_k\tilde V_{k-1}) + q_k,\qquad \tilde V := V/s_c,\quad q_k\in\mathbb{Z}$$

$s_c$ 是權重量化那顆 channel 的 scale,$q_k$ 是乾淨整數,$r(\cdot)$ 的捨入格距
是乾淨的二的冪 $2^{-f_V}$。

目前的實作沒有真的換到這個尺度算,是在原始(未縮放)物理尺度上:

$$V_k = \mathrm{round}\!\left(\frac{a_k V_{k-1}}{s_c\cdot 2^{-f_V}}\right)\cdot s_c\cdot 2^{-f_V} + b_k,\qquad b_k = s_c q_k$$

把 $V=s_c\tilde V$ 代回去,在實數(無限精度)下這兩條式子完全相等——$s_c$
在分子分母代數上剛好消掉。但這個消掉只在實數上成立,浮點數裡 $s_c$ 出現在
兩個獨立算出來的地方($b_k$ 裡的 $s_c$、格距裡的 $s_c$),不會真的互相抵消,
於是「這樣算」跟「換到乾淨整數尺度算」之間有一個誤差量:

$$\varepsilon := \mathrm{round}\!\left(\frac{a_k V_{k-1}}{s_c\cdot2^{-f_V}}\right) - a_k\tilde V_{k-1}\cdot 2^{f_V}$$

只要 $|\varepsilon|<0.5$,捨入的判斷不會被這個誤差翻盤。實測(50 萬組亂數,
參數範圍涵蓋目前 notebook 實際掃描的 $f_V\le14$、權重量化 8 bit 以內):
目前用的範圍下判斷從未被翻盤,但 $\max|\varepsilon|\approx0.125$,已經吃掉
安全邊際($0.5$)的四分之一——$f_V$ 開得更高、或 $s_c$ 數值更極端時,這個
邊際會被壓縮,不是永遠安全。

**根本問題不是「這個誤差量現在夠不夠小」,是這條路徑本身跟 FPGA 會做的事
不是同一個算法**:FPGA 存的是整數暫存器 $\tilde V$、乘一個定點查表值、
移位捨入,全程沒有 $s_c$、沒有浮點除法;目前的模擬版本全程用浮點、
每一步都乘或除 $s_c$。就算數字現在都對得上,這是「兩條不同的路徑巧合
算出一樣的答案」,不是「同一個算法在不同語言裡的兩份實作」。

**處理方式**:讓 `salt_core` 真的提供 $\tilde V$/整數尺度的路徑
(狀態直接存整數、捨入用移位不用除法),不是繼續在物理尺度上模擬。

**$b$ 也是同一個問題,不只 $a$**:追蹤 `AffineMap.b` 的來源鏈,確認目前
存的是

$$b = \hat w = q\cdot s_c$$

不是乾淨整數 $q$ 本身。權重量化那一步($q=\mathrm{round}(w/s_c)$)算出過
$q$,但函式只回傳 $\hat w=q\cdot s_c$ 這個已經乘回去的浮點值,$q$ 沒有被
單獨保留、也沒有流到 `AffineMap.b`——`build_conv_queue_compressed`/
`build_fc_queue` 收到的權重陣列,從頭到尾就是這個已經乘過 $s_c$ 的浮點值,
要拿 $q$ 只能事後用 $\hat w/s_c$ 反推。這代表**整個 AffineMap 的狀態表示法
($a$ 跟 $b$ 兩項)都活在 $s_c$-縮放過的物理尺度,沒有一個地方單獨存在
乾淨整數上**——不是 $a$ 單獨的問題,是同一個架構選擇的兩個面向。

**$v_{th}$ 是第三個受影響的量**:推導文件裡 $\tilde v_{th}=v_{th}/s_c$ 借用
跟 $\tilde V$ 一樣的整數格式,不是獨立參數。但 notebook 實際算
`v_th_quantized` 的方式是:

$$v_{th,\text{quantized}} = \mathrm{round}\!\left(\frac{v_{th}}{s_c}\cdot2^{f_V}\right)\cdot2^{-f_V}\cdot s_c$$

一樣是捨入完再乘回 $s_c$,存的是 $s_c\tilde v_{th}$(物理尺度浮點數),不是
$\tilde v_{th}$ 本身。這個值直接拿去跟同樣是物理尺度的 $V_k$ 比大小做 fire
判斷,兩邊尺度一致、比較本身沒錯,但**跟 $a$、$b$ 同一個道理:這是「換算過、
數值對得上的替身」,不是「硬體暫存器裡真正比較的那個整數」**。

**目前確認受影響的三個量:$a$(查表結果)、$b$(權重貢獻)、$v_{th}$(門檻)
——只要是跟 $\tilde V$ 這個狀態直接運算或比較的量,全部都活在同一個物理
尺度浮點世界裡,沒有一個是乾淨整數。**這三個是目前這輪查到的,不代表沒有
第四個沒查到的量,之後要用整數路徑重寫時,這三個是已知一定要換掉的清單,
但不是「換完這三個就保證完備」的清單。

## 十八、決策:量化捨入慣例——遞迴裡直接對兩補數運算,不拆正負號

**狀態:✅ 慣例已定案(2026-09-26)。目標是跟 FPGA 逐位元一致。**

**起因**:原本兩處捨入都跟著浮點函式庫的預設值走,也就是逢五取偶
($2.5\to2$)。這不是專案選的,FPGA 電路也不太可能剛好這樣做。

第一次修正改成「逢五進一」,但只想到正數。實作時是先取絕對值、
捨入完再把正負號套回去,負數卡在正中間時會往離零的方向走。
這不是電路最簡單的做法。

**定案**:以硬體容易實作為準,直接對兩補數有號數運算,不拆正負號。

- round:先加半格,再算術右移。卡在正中間時往正無窮。
- truncate:直接算術右移,等於 floor(往負無窮),不是往零捨去。

$\div 2$ 的例子,輸入 $[5,-5,3,-3]$(也就是 $[2.5,-2.5,1.5,-1.5]$):

| 做法 | 結果 |
|---|---|
| round(加半格再算術右移) | $[3,-2,2,-1]$ |
| truncate(直接算術右移) | $[2,-3,1,-2]$ |
| 舊做法 round(拆正負號,往離零方向) | $[3,-3,2,-2]$ |
| 舊做法 truncate(拆正負號,往零捨去) | $[2,-2,1,-1]$ |

正數兩種做法結果一樣,負數會差 1。

膜電位本來就會是負值,所以這個差異會真的出現在遞迴裡,
不是只在理論上存在。

**離線換算不受這個慣例限制**:權重碼、門檻、衰減查表碼是離線算一次、
直接存進 FPGA 的整數常數,硬體不會執行這一步。

這一步維持「卡在正中間時往離零方向」,用哪種慣例都不影響逐位元一致。

**乘法拆成高低兩半**:軟體模擬端的 32 位元整數放不下完整乘積,
所以拆成兩半分開乘。拆法跟這個慣例是相容的,推導見膜電位量化推導
「乘法後的捨入」節。

## 十九、決策:$a_k$ 查表直接用整數 $\Delta t$ 當 index,不從 $a$ 反推

**狀態:✅ 已處理。** 整數 $\Delta t$ 從佇列建構一路往下傳,查表直接拿它當
index。下面描述的反推是改之前的做法,留著說明為什麼不能那樣做:目標同上,
是跟 FPGA 逐位元一致。

查表要用哪一格,天經地義應該是拿「經過了幾毫秒」這個整數直接當 index:

$$\text{table\_index} = \Delta t - 1$$

但這個整數 $\Delta t$ 在佇列建構那一步算出來之後,立刻被拿去指數化成
$a=(1-\tfrac1\tau)^{\Delta t}$,只有 $a$ 被留下來,$\Delta t$ 本身沒有跟著
往下傳。等到量化這一步要查表,手上只剩 $a$,只能反推:

$$\Delta t_{\text{recovered}} = \mathrm{round}\!\left(\frac{\ln a}{\ln(1-\tfrac1\tau)}\right)$$

硬體端 $\Delta t$ 是真實時間差的整數計數器,直接拿來當 table index,全程
不會有指數、對數這種運算。這裡是先指數化、再取對數反推,方法上完全是
另一條路——之所以要繞這一圈,是因為 $\Delta t$ 這個整數本來就沒有被設計
成會往下游流動的東西:創建仿射映射那個共用函式收到 $\Delta t$ 之後只回傳
指數化後的 $(a,b)$,$\Delta t$ 本身不是回傳值的一部分,不管是訓練用的路徑
還是量化模擬路徑,共用的都是這個只吐 $(a,b)$ 的函式。

**實測驗證這個反推何時會失真**:當 $a$ 因為 $\Delta t$ 夠大而在 float32
精度下逼近底線(denormal 範圍),連續好幾個不同的 $\Delta t$ 會被捨進同一個
浮點值,反推出來的 $\Delta t$ 會卡住不再增加:

| $\tau$ | 反推開始出錯的 $\Delta t$ | 目前這個 $\tau$ 底下各種 $f_a$ 算出的表深度 | 安全邊際(格數) |
|---|---|---|---|
| 4 | 241 | 12~60 | 181~229 |
| 8 | 518 | 25~129 | 389~493 |
| 16 | 1071 | 53~268 | 803~1018 |
| 32、64 | 測到 2000 都沒出錯 | 109~1100 | 更寬 |

**為什麼這個發現比前兩節更值得認真看待**:$a$/$b$/$v_{th}$ 活在物理尺度、
捨入用逢五取偶,這兩件事影響的是「這一步算出來的數值精不精確」;這一節
的問題不一樣——查表這個動作存在的唯一理由,就是要模擬「硬體真的去查表」
這件事本身,如果連查表用的 index 是怎麼決定的都跟硬體是兩條路,那這個
模擬工具的核心任務就沒有真正做到,只是目前的參數範圍剛好沒被撞到。

**跟整個專案的關聯**:這份膜電位量化模擬的目的,不只是這次拿來選一組
$(b,i_V,f_V,f_a,r)$ 參數的一次性分析——專案的目標是訓練出的模型行為要
跟 CSNN-FPGA 的逐事件 forward pass 完全對得上,之後要做 bit-exact 的硬體
驗證。這代表現在這份模擬很可能就是將來拿去跟真正晶片輸出逐位元比對的
基準。如果模擬用的方法跟硬體本來就不是同一條路,只是數字在目前測過的
範圍內剛好一致,將來換了參數範圍、換了訓練資料使某層 $\tau$ 落在不同區間,
這個反推可能在沒人注意到的角落開始出錯,而且會被誤判成「硬體那邊做錯」,
而不是「模擬工具的方法本來就有問題」。

**處理方式**:讓創建仿射映射的共用函式把 $\Delta t$ 這個整數也一起
傳出來,量化路徑直接拿真正的整數當 table index,不要反推。
