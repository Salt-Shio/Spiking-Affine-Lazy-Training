## N-MNIST 資料集(2026-09-02)

選用真實事件相機資料集(N-MNIST),不是自建 latency encoding——資料本身就是 (x,y,polarity,t),事件數量不固定,跟專案「處理真實非同步事件流」的目標最貼近。已下載至 `event_lif/data/datasets/N-MNIST/`。

**格式**(官方規格,已用全部 70000 個檔案實測驗證):34×34、2 channel(ON/OFF)、40-bit AER(X 8bit/Y 8bit/polarity 1bit/timestamp 23bit,單位微秒)。事件數分布:min 652、max 8183、mean 4176.5、p99 6727。

**編碼規格**:

| 項目 | 決定 |
|---|---|
| 時間量化 | `t_微秒 // 1000`(floor,對齊 FPGA 慣例) |
| 同毫秒 tie-break | 檔案原始順序 |
| stabilize.m 運動補償 | 不做(先驗證管線通不通,不驗證空間局部性假設) |
| Polarity → channel | c=0(OFF)、c=1(ON) |
| 事件數截斷/padding 長度 | **2000**(每個樣本只取前 2000 筆事件,超過的截斷;不足的 pad。2026-09-03 改定案,原本是 8183 全資料集真實最大值無截斷,理由見下方說明) |
| Batch size | 不強制,能跑起來優先(2026-09-03 放寬,原本寫 4) |
| Train/Val 切分 | Train 60000 筆切 10% 當 val(簡單隨機) |
| 第一次訓練規模 | train 1000 / val 200 / test 200 |
| 檔案位置 | `event_lif/data/src/nmnist.py` + `event_lif/data/tests/test_nmnist.py` |

**事件數截斷長度為什麼改成 2000(2026-09-03)**:原始決定(padding 到全資料集最大值 8183、不截斷)在實作 conv 訓練腳本時撞到記憶體問題——conv 事件佇列是密集陣列,長度等於事件數,`run_layer_forward` 對這個長度做 `jax.lax.scan` 反向傳播,記憶體需求跟這個長度近似成正比(這是 dense 佇列表示法本身的已知代價,`docs/conv事件佇列建構推導.md` 第 10 節本來就列為擱置項目,不是這次新發現的 bug)。用真實資料視覺化不同截斷長度重建出來的影像,發現 N-MNIST 對同一張靜止數字做 3 輪掃視,**前 200~1000 筆事件就能重建出完整輪廓,把全部事件疊起來反而因為重複掃視互相抵消變成雜訊**——這只驗證了「空間形狀多早就夠」,不是「SNN 訓練準確率多早就夠」,兩者要分開看。實際截斷長度沒有抓「輪廓剛好夠用」的最激進值(200~1000,會砍掉幾乎每個樣本 2/3 的事件),而是抓「剛好緩解記憶體問題」的溫和值:2000 這個長度,量測(3000 筆隨機樣本)顯示會截斷 96.7% 的樣本,砍完之後從圖上看輪廓仍然清楚可辨(比 4000 銳利,比 8183/全部好非常多)。Batch size 同時放寬為「不強制」,訓練目標從「規格書寫 4」改成「先讓 POC 真的跑起來、學會分類」,batch size 多少配合記憶體實際狀況調整。

## conv 網路架構(2026-09-02)

只用 conv+FC,不用 pooling。

$$\text{conv1} \to \text{conv2} \to \text{flatten} \to \text{FC(輸出層)}$$

| 層 | 規格 |
|---|---|
| conv1 | $IC{=}2,OC{=}8,K{=}3,S{=}2,P{=}1$(輸入 $34\times34\to17\times17$) |
| conv2 | $IC{=}8,OC{=}16,K{=}3,S{=}2,P{=}1$($17\times17\to9\times9$) |
| FC(輸出層) | flatten 後 $1296\to10$ |

conv1/conv2 是會 fire 的隱藏層;FC 輸出層 $v_{th,out}=1e9$,不 fire,純積分器,10 個 $v_{final}$ 當 logits 送 `softmax_cross_entropy`。

**超參數**:$\tau=16.0$、$\alpha=2.0$、$v_{th,hidden}$(conv1/conv2 起始值)$=1.0$。`init_k`(權重初始化縮放,$limit=init\_k/\sqrt{fan\_in}$):**三層全部 `5.0`,committed 值,不校準**(2026-09-08 定案)。

> **2026-09-08 修正**:下面關於 `init_k` 掃描的段落(段 3.8 定案 / 執行結果:conv1=8.0、conv2=64.0)**已廢棄**。firing-rate 目標帶 $[0.20, 0.50]$ 當 init_k 選值準則會把 init_k 推進「單筆事件就 fire」的飽和區,訓練較差(V6 實測:8/64 ≈ 0.735 vs `init_k=5` ≈ 0.80,10 epoch 同 seed)。完整推導(膜電位穩態變異數 → 命中帶必然飽和 → surrogate 斜率崩 → Lee 變異數保持準則)+ 數值驗證 V1–V6 見 `docs/math/初始權重尺度推導.md`;問題紀錄第十二節、`salt_core/架構問題盤點.md` §1.5 同步更新。段 3.8 的 $L_1$ 幾何量測與此無關,仍有效。以下段 3.8 內容保留為當時脈絡。

任務 7 舊掃參結果 `init_k=5.0`/conv1 14.9%/conv2 2.2% —— 這組**反而是對的方向**(見上方修正)。**這組數字目前還不能直接回填 `baseline.yaml`**:`ConvNetCompressedConfig`/`_init_conv_params` 只有單一 `init_k` 欄位、三層共用同一個值,不支援 conv1/conv2 各自不同的數字——這是 2026-09-05 才發現的缺口,要先擴充 config schema(拆成 per-layer 欄位)才能真正套用,見下方待辦。**FC 輸出層不進掃描(`v_th_out=1e9` 不會 fire,firing rate 判準對它沒有定義),固定 `init_k_fc=5.0`(2026-09-06 定案)**——沿用任務 7 那組 84.5% val_accuracy 密集版 POC 實際用過的值,理由:(1) FC 是純積分器,不像 conv1/conv2 需要命中 firing rate 目標帶,沒有「正確值」可掃,初始尺度只要不極端,訓練過程中優化器會自行校正;(2) `limit=5/\sqrt{1296}\approx0.139` 量級不極端;(3) 5.0 已經在同一個 FC 層的角色上有實測收斂先例,不是新猜的數字。

### 段 4 定案:等價測試(2026-09-04)

**grad 會不會一樣**:會,而且不是新的未知數——段 1 的測試(`test_conv_queue_compressed.py`)本來就比對過 `grad_dense` vs `grad_compressed`(對 conv 權重的梯度),多個隨機 seed 都通過。壓縮版跟密集版是同一組仿射運算,只是把不影響數值的 identity/衰減步驟用封閉式 catch-up 衰減一次算完,forward 等價 ⇒ JAX 反向傳播自動給出等價的 grad,不需要另外設計梯度邏輯。段 4 要新驗證的不是「grad 會不會一樣」(已知答案),是這個等價性**穿過 conv1→conv2→FC 整條 cross-layer 鏈**、在**真實 N-MNIST 規模**下是否還成立——段 1 只測過單層、小規模。

**容差**:`atol=1e-4`(絕對容差,不用 `rtol`——`v_final`/梯度接近 0 時 `rtol` 會失真),沿用段 1 `test_conv_queue_compressed.py` 已經在用、審查過、通過的數字(小規模確定性案例用 `1e-6`,隨機案例用 `1e-4`);N-MNIST 規模事件數遠多於段 1 的 30 事件壓力測試案例,浮點誤差累積只會更多不會更少,`1e-4` 是合理延伸不是新猜的數字。

**測試覆蓋範圍**:

| 比對對象 | 內容 |
|---|---|
| forward | `v_final`(logits)、`spike_mask`、輸出事件,`ConvNetCompressed` vs `ConvNet` |
| grad | 對 `ConvNetParams` 三個分量(`w_conv1`/`w_conv2`/`w_fc`)分別比,不能只看聚合 |
| loss 選擇 | 主要驗證用簡單、隔離用的 loss(比照段 1,例如 `v_final` 直接取分量或求和);再至少一組用 `train_conv.py` 實際的 `softmax_cross_entropy` loss 確認 loss wrapper 沒破壞等價性 |
| 規模 | 段 1 沿用的小規模手算案例(邊界情況)+ 真實 N-MNIST 樣本(production `max_events=2000`) |
| $L_1$/$L_2$ 設定 | 測試裡 `ConvNetCompressed` 的 $L_1$、$L_2$ 都用開大值(不截斷),測的是「壓縮機制本身對不對」,不是「緊 $L_1$/$L_2$ 夠不夠」 |

**這個測試只需要 forward 一次 + `jax.grad` 一次,不需要跑訓練迴圈**(不 `optax` 更新權重、不跑多個 epoch、不需要 optimizer state)——比的是「兩個模型在同一組固定權重下算出來的東西一不一樣」,不是訓練會不會收斂。

#### 程式結構與 config(2026-09-04)

| 決定點 | 內容 |
|---|---|
| `ConvNetCompressed` 放哪 | **跟 `ConvNet` 同一個檔案**(`src/models/conv_net.py`),不另開新檔。先例:`build_conv_queue`(密集)/`build_conv_queue_compressed`(壓縮)本來就同檔放在 `connectivity/conv.py`,壓縮版專屬輔助函式也跟著放進去,沒有另開檔案。同檔才能直接共用 `CONV1`/`CONV2` 幾何常數、`_receptive_field_opportunity_count`、`conv_layer_receptive_field_firing_rate`,不用跨檔案 import |
| Params 型別 | **重用 `ConvNetParams`**,不新開型別——壓縮只改變佇列怎麼建,不改變權重張量形狀(`w_conv1`/`w_conv2`/`w_fc` 兩版完全一樣) |
| $L_1$/$L_2$ 進不進 `baseline.yaml` | **段 4 階段不進**。原則跟段 3.7 一致:只有真正被消費、數值已確定的東西才進 yaml。$L_1$ 段 4 階段還沒被 3.8 量出來;$L_2$ 連欄位語意都還沒定案(初始猜測值?硬性上限?段 5 動態放大後的當前值?)。段 4 等價測試裡 $L_1$/$L_2$ 用測試檔自己定義的開大常數建構 `ConvNetCompressedConfig`,不從 config 讀。$L_1$ 欄位等 3.8 量出真實值才加進 `baseline.yaml`;$L_2$ 欄位等段 5 設計出動態機制、語意確定後才加 |
| `max_steps` | `run_layer_forward` 自己的 docstring 已講明:`max_steps = L`(佇列長度)不管密集版還是壓縮版都永遠安全。密集版另外調小 `max_steps_conv2`/`max_steps_fc` 是因為密集版陣列寬度刻意留很寬(全域事件數當安全邊界防截斷),scan 真正要跑的步數可以比陣列寬度小很多;壓縮版陣列寬度本身就是 $L$(已經是每顆神經元的緊緻長度),沒有「陣列比實際步數更寬」這件事,$L$ 本身就是最緊的安全步數。**結論**:`ConvNetCompressed` 的 conv1/conv2 用 $L_1$/$L_2$ 同時當佇列長度跟 `max_steps`,原本的 `max_steps_conv2` 欄位對壓縮版沒有意義、拿掉;`max_steps_fc`(FC 沒有壓縮,仍是密集版)、`max_spikes_conv1`/`max_spikes_conv2`(`extract_output_events` 輸出事件數上界,跟佇列長度是不同概念)兩版都要,保留 |
| 測試檔案 | 新增 `src/tests/test_conv_net_compressed_equivalence.py`,跟既有 `src/tests/test_conv_net_forward.py` 同一種命名慣例 |

### 段 3.8 定案:init_k 掃描與 $L_1$ 量測(2026-09-04)

**前提**:段 3.8 排到段 4 之後才做——init_k 掃描的目標模型是實際拿去訓練的
`ConvNetCompressed`,不是即將降級為參考基準的密集版 `ConvNet`(理由見段 4 那格)。
`ConvNetCompressed` 可以在 $L_1$ 未知前用開大值先建出來,順序上不衝突。

**任務 7 舊數值全部作廢**,不當起點也不當參考:`init_k=5.0`、conv1 14.9%@5.0 /
conv2 2.2%@5.0 那組 firing rate、任何舊 $L_1$ 估計。

#### A. init_k 掃描

| 決定點 | 內容 |
|---|---|
| 掃描性質 | firing rate 對 init_k 統計上單調遞增 → bracket(倍增/減半找上下界)+ bisection,不是網格搜尋 |
| per-layer | 依前向順序序列化掃描:上游層 init_k 凍結後才掃下游層(conv1 先定 → 凍結後掃 conv2) |
| 哪些層進掃描 | 由 config 明確列出要掃描的層清單,不靠「會不會 fire」自動判斷;沒列進清單的層(如 FC 輸出層 `v_th_out=1e9` 純積分器)給固定 init_k,不進掃描——firing rate 對它恆為 0,沒有訊號 |
| 度量 | receptive-field 正規化 firing rate(`conv_layer_receptive_field_firing_rate` 那套邏輯的通用版):每層用「落進自己感受野的事件數」當分母,只對分母 > 0 的神經元取平均;FC 層感受野=全部事件,公式自然退化成樸素版,同一套機制通吃 |
| 目標帶 | 單一可調參數,預設 `[0.20, 0.50]`,所有要掃的層共用同一個帶 |
| 掃不到怎麼辦 | 合理範圍(例如 init_k∈[1e-3,1e3])內找不到能進帶的值 → 報錯 + 印 firing rate vs init_k 曲線,不靜默挑最接近 |
| 掃描規模 | 256 筆、**均勻隨機抽樣**、固定 seed(2026-09-05 修正:原寫「依 class 分層抽樣」,實測 N-MNIST 每類筆數在 5421~6742 之間、差距 <25%,均勻隨機抽 256 筆的類別比例波動遠小於 firing rate 量測本身的統計噪聲,不需要嚴格分層,也不新增 `NMNISTDataset` 的分層抽樣 API);選定值用大樣本(4000 筆)確認,掉出帶外就加大子集重掃 |
| `max_events` | 沿用現行 2000,跟 production 訓練用的值一致(2026-09-04 確認) |
| 通用性 | 判準不寫死 conv/FC,未來新增會 fire 的層(例如 FC1 隱藏層)要能直接套用同一套規則 |

#### B. $L_1$ 量測

沿用 `_receptive_field_opportunity_count`,對 train+val+test 全資料集跑一次取最大值。這個量只跟事件座標、K/S/P 幾何有關,跟權重/訓練過程無關,training-independent,算一次永久有效。跟 A 一樣在 `max_events=2000` 下量。

#### 程式結構(2026-09-04 定案)

| 檔案 | 內容 | 通用程度 |
|---|---|---|
| `src/init_k_search.py`(新檔) | `FiringLayerHooks`(NamedTuple:設 init_k / 跑前向到該層 / 量 firing rate 三個 hook)+ `sweep_init_k(layers, band, ...)` 純函式(bracket+bisect 迴圈) | 完全通用,不知道 conv/FC/N-MNIST 是什麼,之後任何架構(例如未來加 FC1 隱藏層)直接 import,不用改這支檔案 |
| `ConvNetCompressed` 模組旁 | $L_1$ 量測函式,緊貼壓縮佇列幾何(`_receptive_field_opportunity_count`) | 只有會壓縮佇列的層需要,FC 永遠用不到,不進通用模組 |
| `src/conv_param_search.py`(降級成 CLI 膠水層) | 建 conv1/conv2 的 `FiringLayerHooks` 清單 → 呼叫 `sweep_init_k` → 呼叫 $L_1$ 量測 → 輸出結果 | 只有這支知道「這個專案現在有哪些層」 |

選 function(而非 class)的理由:掃描無跨呼叫狀態,是純輸入輸出的演算法,跟既有
核心邏輯(`build_conv_queue`/`run_layer_forward` 等自由函式)同一種寫法;既有的
`ConvNet`/`FCNet` 這種 class 只用來綁 config + 串 `init`/`apply` 給單一固定架構,
不是這裡要的東西。

**明確排除**:不借這次機會把 `ConvNet`/`ConvNetCompressed`/`FCNet` 改寫成通用多層
組裝器(`(layer_type, config)` 那種)。`docs/問題紀錄.md` 第二節已把這個列為明確
擱置的架構債務,`FiringLayerHooks` 只是為掃描用途的薄封裝,不是提前還這筆債。
